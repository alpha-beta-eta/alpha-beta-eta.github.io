第1章 用shift和reset编程导论

这个关于定界延续的教程是与浅井健一 (Kenichi Asai, 御茶水女子大学, 日本) 一起在2011年延续研讨会 (Continuation Workshop 2011) 前夜给出的.

延续的概念在编程中自然地出现: 条件分支从两个可能的未来中选择一个延续; 引发一个异常丢弃延续的一部分; 一个尾调用或者goto以该延续继续. 尽管延续在每个语言中都被隐式地操纵, 将它们作为第一级对象显式地操纵却很少被使用, 因为人们觉得这很困难.

这个教程旨在给出延续的一个平缓的导论, 以及使用控制算子shift和reset以第一级定界延续进行编程的初步体验. 不假定有关于延续的预备知识, 这个教程帮助参与者编写简单的协程和非确定性搜索. 这个教程应该使得理解和欣赏CW 2011上的报告变得更容易.

我们假定读者对于函数式编程语言有基本的了解, 例如OCaml, Standard ML, Scheme和Haskell. 不需要关于延续的预备知识. 我们鼓励参与者带上笔记本电脑并跟着编程.

第2章 Slide-Effect: 幻灯片叠层和定界控制

或许每个做过PowerPoint, Beamer或者普通老式幻灯片演示的人都尝试过叠层 (overlay): 一种通过逐步显示或者隐藏幻灯片的某些内容来让幻灯片动起来的简单方式. 然而, 可能没有多少人意识到他们这样做时体验到了定界控制. 何以如此——本文对此加以阐述. 我们将会看到定界控制是相当普遍的. 它甚至可以在编程语言或者系统中没有专门的定界控制设施的情况下实现. 我们也会看到这种设施——定界控制算子——如果真的可用的话, 能带来什么. 定界控制的专家在这里或许也能看到一些东西: 多发 (multi-shot) 定界控制的一个现实的例子——这种定界控制被认为很少被使用也很少有用, 因此在一些系统中甚至不被提供.

我们的贯穿始终的例子是一个相当典型的带有叠层的Beamer幻灯片:

    \begin{frame}{My Slide}

    This is my talk

    It has several points

    \begin{itemize}
    \item First, me have to mention this
    \only<2,3,4>{\item Then it comes to that}
    \only<3>{\item We have to stress that}
    \only<4>{\item Or, to put it better,}
    \end{itemize}

    \note<1>{To expand on 1}
    \note<2,3,4>{Note on 2}
    \note<4>{Note on 4}
    \note<3,4>{Note on 3}
    \end{frame}
这里, \only<numbers>{content}的意思是content只出现在numbers中列出的叠层上 (\note<X>{Y}本质上是\only<X>{\note{Y}}的简写). 因此, 这个幻灯片有四个叠层 (因为4是所提及的最大的叠层编号). 在第一个叠层上, 列表只有单独一个, 也就是最上面的, 项 (附带着第一个注记, 显示与否取决于Beamer的设置). 这个项以及其上方的文本一直保留到最后. 第二个叠层带来了第二个列表项 (以及相关联的注记), 它们也会持续存在. 下一个叠层添加了第三个项, 它在最后一个叠层中被替换. 当然, Beamer还有其他叠层算子——它们要么可以用\only来实现, 要么可以类似地实现. 因此, 我们将自己限制于\only.

我们描述\only的两个实现: 不带有定界控制的和带有定界控制的, 并对它们加以对比. Beamer是用TeX写的, 而TeX并不是呈现算法 (或者一般地编程) 的最佳语言. 我们转而使用OCaml. OCaml (至少到4.14版本为止) 具有一个通用的定界控制设施 (delimcc库), 它在第二个实现中被使用.

Beamer接受上面的幻灯片TeX代码并创建输出的若干pdf页面, 每个叠层一页. 在我们的OCaml实现中, 我们专注于叠层展开, 跳过排版和pdf渲染. 也就是说, 我们接受一个带有叠层算子的帧 (frame) 并将其展开为一个渲染好的帧的列表, 其中没有叠层算子. 一个帧在OCaml中以或许最为朴素的方式被表示, 即作为frame数据结构:

    type frame = Frame of string * content list
     and content =
      | Lit of string
      | List of content list
      | Note of content
      | Empty

    let frame t c = Frame(t,c)
帧的内容由字面字符串, 列表和注记构成——刚好足够我们的贯穿始终的例子. 人们可以很容易地将其渲染为markdown, html或者任何其他格式.

对于叠层, 我们假定最为极简的接口:

    module type framer = sig
      val make_overlays : (unit -> frame) -> frame list
      val only : int list -> content -> content
    end
函数make_overlays接受一个可能包含only的帧表达式 (表示为一个thunk)——并返回完成了的帧的列表, 每个叠层一个. 可能出现在叠层表达式中的函数only只在所列出的叠层上显示其content. 以下是示例Beamer幻灯片在OCaml中的表示方式——这相当于一个用于带有叠层的幻灯片的简单嵌入式DSL.
    module Ex(S:framer) = struct
      open S

      let r = make_overlays @@ fun () ->
      frame "My Slide" [
       Lit "This is my talk";
       Lit "It has several points";

       List [
         Lit "First, we have to mention this";
         only [2;3;4] @@ Lit "Then it comes to that";
         only [3] @@ Lit "We have to stress that";
         only [4] @@ Lit "Or, to put it better,";
       ];

       only [1] @@ Note (Lit "To expand on 1");
       only [2;3;4] @@ Note (Lit "Note on 2");
       only [4] @@ Note (Lit "Note on 4");
       only [3;4] @@ Note (Lit "Note on 3");
     ]
    end
显然, 用OCaml写幻灯片比用TeX写要不方便得多 (这种不方便可以通过带有可选参数的智能构造器在一定程度上得到缓解, 或者, 更好的是, 使用ppx预处理器). 我们显式地以framer接口的实现参数化了代码: 我们将会有两个实现.

framer的第一个实现是叠层展开在Beamer中很可能的实现方式. 想法很简单: 不断地重新执行帧表达式, 在不同的动态环境中: 带有不同的当前叠层编号. 算子\only<numbers>{content} (或者, 在OCaml中, note [numbers] content{译注: 此处应为only numbers content}) 会省略其content, 除非当前叠层编号列在numbers之中.

    module FramerState : framer = struct
      let curr_frame = ref 0
      let max_frames = ref 0

      let make_overlays th =
        curr_frame := 1;
        max_frames := 1;
        let rec loop f =
          if !curr_frame >= !max_frames then [f] else
          (incr curr_frame; f :: loop (th ()))
        in loop (th ())

      let only ixs c =
        let mx = List.fold_left max 1 ixs in
        if !max_frames < mx then max_frames := mx;
        if List.mem !curr_frame ixs then c else Empty
    end
FramerState字面上实现了这个想法: 它是一个可执行的规格. 其唯一的复杂之处在于叠层的数目并不是事先已知的, 而是必须在展开期间确定: 它是only中所提及的最大的叠层编号.

其缺点, 即全局可变状态, 也是明显的. 考虑如果make_overlays在帧内容之中被递归地调用会发生什么: 这可能是因为失误而发生的; 这也是正当的, 用以格式化一个迷你帧. 尽管可变状态可以经过一些加工而被隐藏起来, 它却是不可避免的: 它是make_overlays和only之间的通信渠道.

FramerState最大的缺点, 不得不承认, 是审美上的: 一遍又一遍地从头重新渲染一切, 就是让人感觉不对. 在我们的示例幻灯片上, 第一个列表项以及其上方的文本保持不动. 这一部分肯定可以一劳永逸地渲染一次, 然后在所有的输出页面之间共享吧? 类似地, 列表中的第二个项出现在叠层2, 3和4上. 渲染到这个列表为止一次, 然后在输出中共享, 难道不好吗?

正是这样的思路引向了定界控制. 考虑来自我们的贯穿始终的例子的帧表达式, 在下面重复如下:

    frame "My Slide" [
     Lit "This is my talk";
     Lit "It has several points";

     List [
      Lit "First, we have to mention this";
      only [2;3;4] @@ Lit "Then it comes to that";
      only [3] @@ Lit "We have to stress that";
      ...
     ]
在从左到右的求值中, 我们首先求值Lit "This is my talk", 然后是Lit "It has several points", 然后进入List表达式并求值其第一项. 求值在堆上构建content数据结构, 将它们链接起来并从栈上引用它们. 现在我们来到第一个only. 叠层的公共部分在这里结束: 一些叠层以Lit "Then it comes to that";继续, 一些则不带有它. 无论哪种情况, 到这一点为止的栈都是共享的. 定界控制恰恰就是从一个选择点恢复, 并共享在此之前获得的结果的机制.
    module FramerCont : framer = struct
      open Delimcc
      type req = Done of frame
               | OnlyAt of int list * content * (content -> req)

      let p = new_prompt ()
      let only ixs c = shift0 p (fun k -> OnlyAt (ixs,c,k))
    ...
如同在FramerState中那样, 操作make_overlays和only进行通信: 这一次, 使用的是控制而非可变状态. (顺便一提, 可变状态可以用定界控制来模拟这一点很早就被注意到了.) 这种通信是单方面的且简单的: only将其参数报告给接收者 (也称为处理器: make_overlays的一部分) 并让它做所有的工作. 关键在于, only捕获了栈在其求值点处的部分, 作为延续k. 当这个延续被调用时, 帧表达式的求值从所保存的点继续. 这个延续可以被调用若干次: 所有这些恢复都始于同一个共享的栈.

函数make_overlays尝试在only numbers content上继续求值两次: 一次是为了列在numbers中的叠层 (因而包含content), 一次是为了没有列出的叠层. only的延续可能包含另一个only: 另一个选择点. 然而, 并非所有的选择都是可能的, 因为only的一个延续对叠层编号施加了约束. 函数make_overlays追踪这些约束: 细节请参见源代码. 总而言之, FramerCont在构建叠层的同时维持了共享并避免了不必要的重新求值.

我们应该强调, only的延续k被调用 (恢复) 了两次: 即所谓的多发定界控制. 从版本5开始, OCaml以代数效应的形式提供定界控制——然而, 它是一发的: 一个被捕获的延续只能被恢复一次 (常常是几乎立即恢复). 这确实是定界控制最常见的用法. 多发定界控制对于表示非确定性是不可或缺的 (参见Hansei概率编程库)——而通常认为, 对于其他任何东西则并非如此. 看到多发定界控制的另一种用途, 是有些令人惊讶的 (对我来说也是如此).

PDF本身就有叠层, 或者说过渡——尽管除了Acrobat之外, 似乎很少有阅读器实现了它. 如果要编写一个支持过渡的PDF阅读器, 或许本文可以作为参考. 或许人们甚至会想要使用定界控制...

第3章 定界控制与广度优先, 深度优先以及迭代加深搜索

这份教程式的Haskell代码阐明了定界控制在非确定性搜索中的应用. 我们将不同的搜索策略应用于同一个非确定性程序, 而不必重写它. 一个非确定性计算被具体化为一个惰性搜索树, 然后可以以不同的方式检查这个搜索树. 我们将非确定性搜索策略写成标准的深度优先, 广度优先等等的树遍历.

搜索树是普通的树数据类型, 其分支按需构造. 这个树可能是无穷的, 下面的例子中就是如此.

    data SearchTree a = Leaf a | Node [() -> SearchTree a]
我们实现三种树遍历, 它们将来自叶结点的值收集到一个列表之中:
    dfs, bfs, iter_deepening :: SearchTree a -> [a]
(实际上我们使用了广度优先搜索的若干个版本, 它们被优化到了不同的程度.)

使用来自标准单子变换器库的Cont单子及其操作shift和reset, 我们实现了两个原语: 从一个有限列表中非确定性地选择一个值, 以及将一个计算具体化为一个SearchTree:

    choose :: [a] -> Cont (SearchTree w) a
    reify  :: Cont (SearchTree a) a -> SearchTree a
其他非确定性操作——failure, mplus (用以连接两个计算), choose' (用以从一个可能无穷的列表中选择)——都是用choose写的.

贯穿始终的例子是一个真实的归纳编程问题的简单版本: 给定一个输入-输出对的序列[(Int,Int)], 找到一个具有该输入-输出行为的Int->Int函数. 要在其中搜索的函数由以下数据结构表示:

    data Exp =
      K Int                                 -- constant function
      | X                                   -- identity
      | Exp :+ Exp                          -- \x -> f x + g x
      | Exp :* Exp                          -- \x -> f x * g x
解法是熟悉的生成并测试
    induct io = reify $ do
      exp <- an_exp
      if all (\ (i,o) -> eval exp i == o) io then return exp else failure
其中an_exp生成一个样本函数表示, 而if表达式测试在给定输入上对其求值是否给出所欲的输出. Exp表达式的生成器是
    an_exp =
      (fmap K $ choose numbers)   `mplus`
      (return X)                  `mplus`
      (liftM2 (:+) an_exp an_exp) `mplus`
      (liftM2 (:*) an_exp an_exp)
     where numbers = [-2..2]
深度优先搜索不能用于这个问题, 因为搜索树是无穷的. 广度优先和迭代加深都是完备的策略, 如果答案存在的话, 它们都能找到答案. 例如, 对于输入-输出对的序列[(0,1), (1,1), (2,3)], 我们找到了K 1 :+ (X :* (K (-1) :+ X)) (其对应于函数1 + x*(x-1)), 它确实具有给定的行为. 在一个稍大一点的问题[(0,1), (1,1), (2,3), (-1,3)]上的基准测试表明, 优化了的广度优先搜索占用303MB, 而迭代加深占用64MB的内存 (并且时间大致相同). 尽管是玩具, 这个归纳编程问题并不简单. 对于输入-输出对[(0,1), (1,3), (-1,3), (2,15)], 广度优先搜索很快就分配了8GB并被内核杀死. 迭代加深分配的速度要慢得多, 但仍然达到了8GB并且同样死掉了.

第4章 如何移除动态提示符: 静态和动态的定界延续算子是同等可表达的

这份技术报告表明, 定界延续算子shift, control, shift0等等全都可以用彼此宏表达. 此外, 算子shift, control, control0, shift0是单个参数化族的成员, 并且标准的CPS就足以表达它们的指称语义.

这份报告形式化地证明了经由shift实现的control确实具有其标准的归约语义.

第5章 不流泪的回答类型修改: 有类型定界控制算子的提示符传递风格翻译

定界控制算子的显著特性是它们在计算期间修改回答类型的能力. 这个特性, 即回答类型修改 (answer-type modification, 简称ATM), 让人们能够紧凑而漂亮地表达各种有意思的程序, 例如有类型的printf, 然而它也使得将这些算子嵌入标准的函数式语言变得困难. 在这篇论文中, 我们呈现了一个有类型的翻译, 将带有ATM的定界控制算子shift和reset翻译为一个熟悉的带有多提示符shift和reset而不带有ATM的语言, 这让我们能够在标准语言中使用ATM而不必修改类型系统. 我们的翻译推广了Kiselyov的有类型printf的直接风格实现, 后者使用两个提示符来模拟回答类型的修改, 并在计算期间传递它们. 我们证明了我们的翻译保持类型. 由于朴素的提示符传递风格翻译即使对于纯的项也会生成并传递许多提示符, 我们给出了一个优化了的翻译, 其只在需要时才生成提示符, 并且也是保持类型的. 最后, 我们给出了一个tagless-final风格的实现, 其由构造而尊重类型.

第7章 带有有类型提示符的定界控制的简单类型lambda演算不是强规范化的

简单类型lambda演算具有强规范化性质: 任何项的任何归约序列都会终止. 如果我们添加带有有类型提示符的定界控制算子 (例如cupto), 强规范化性质就不再成立. 单个有类型提示符就已经导致不终止. 以下例子是由Chung-chieh Shan从带有动态绑定的简单类型lambda演算的不终止例子设计而来的. 它使用了OCaml定界控制库. 函数loop本质上是fun () -> Omega: 其推断出的类型是unit -> 'a; 因此, loop ()的求值会永远循环下去.

    let loop () =
      let p = new_prompt () in
      let delta () = shift p (fun f v -> f v v) () in
      push_prompt p (fun () -> let r = delta () in fun v -> r) delta

Chung-chieh Shan也给出了解释: 作为箭头类型的回答类型隐藏了一个递归类型. 换言之, delta的类型unit -> 'a隐藏了回答类型以及这个函数不纯的事实.

Olivier Danvy好心地指出了他和Andrzej Filinski在1998年使用他们在SML/NJ中实现的shift版本设计的类似的不终止例子. 他们的例子也依赖于作为箭头类型的回答类型.

第8章 定界延续的一个子结构类型系统

我们提出抽象地解释小步而非大步操作语义的类型系统. 我们将一个表达式或者求值上下文视为带有假设推理的线性逻辑中的一个结构. 求值顺序不仅由操作语义中熟悉的聚焦规则所调控, 也由类型系统中的结构规则所表达, 因此类型更紧密地追踪控制流. 绑定上下文和求值上下文是相关的, 但后者是线性的.

我们使用这些想法为定界延续构建一个类型系统. 它让控制算子能够改变回答类型或者在最近的动态包围定界符之外起作用, 却不需要在判断和箭头类型中有额外的字段来记录回答类型. 一个直接风格程序的定型推导将其去糖为延续传递风格.

第9章 传名的有类型shift/reset演算

我们呈现一个Church风格的传名lambda演算, 其带有定界控制算子shift/reset以及第一级上下文. 除了常规的lambda抽象——其允许对一般的, 甚至是带有效应的项进行代换——这个演算也支持严格的lambda抽象. 后者只能被应用于值. 由reset和严格函数施加的对于值的需求决定了求值顺序. 这个演算与熟悉的传值shift/reset演算最为紧密地对应, 并在严格函数的帮助下嵌入了后者.

这个演算是有类型的, 既给项指派类型, 也给上下文指派类型. 类型抽象地解释操作语义, 因而简明地描述了一个项的求值中可能发生的所有效应. 纯类型被赋予那些其求值在任何上下文中以及在绑定项的自由变量 (如果有的话) 的任何环境中都不招致效应, 即不包含shift转换的项. 一个其求值可能包含shift转换的项具有一个带有效应的类型, 其描述了这个项的最终回答类型以及这个项的求值所需要的定界上下文. 控制算子可以改变其上下文的回答类型.

第10章 来自有类型prompt/control的不动点组合子

在最近的论文Typed Dynamic Control Operators for Delimited Continuations中, 亀山和米澤 (Kameyama and Yonezawa) 在他们的用于prompt/control的多态有类型演算中展示了一个发散的项. 因此, 与浅井和亀山的多态有类型shift/reset演算相对, 后者这个演算不是强规范化的. 与无类型的情形不同, 有类型的control不能用shift宏表达. 亀山和米澤猜想 (有类型的) 不动点算子在他们的演算中也是可表达的. 这个猜想是正确的: 以下是不动点组合子的推导, 使用了他们论文的记号. 然而, 这个组合子并不是完全多态有类型的: 结果类型必须是有居留元的.

令f是一个类型为a→a的纯函数, 而d是一个类型为a的值 (在论文中, d写成一个黑点). 如同在论文中那样, 我们将提示符写成#. 表达式 # ( controlk . ( f # ( kd ; kd ) ) ; controlk . ( f # ( kd ; kd ) ) ) 看起来是良类型的. 它归约为 # ( controlk . ( f # ( kd ; kd ) ) ; controlk . ( f # ( kd ; kd ) ) ) ⟶ # ( f # ( kd ; kd ) ) ⟶ # ( f # ( f # ( kd ; kd ) ) ) ⟶⁎ # ( f # ( f # ( f… ) ) ) 其中ku=u;controlk.(f#(kd;kd)).

既然我们处于一个传值语言之中, 上面的结果并不是非常有用, 但这是一个好的开始. 我们只需要一个eta展开: 假设f具有类型(a→b)→(a→b). 令d是类型a→b的任意值: 这是返回类型有居留元的见证. 我们构建项 FX= # ( controlk . ( f ( λx. # ( kd ; kd ) x ) ) ; controlk . ( f ( λx. # ( kd ; kd ) x ) ) ) 其是良类型的, 并且展开为 FX ⟶ # ( f ( λx. # ( kd ; kd ) x ) ) ⟶ f ( λx. # ( kd ; kd ) x ) 其中ku=u;controlk.(f(λx.#(kd;kd)x)). 注意到kd是controlk.(f(λx.#(kd;kd)x)), 我们得到f(λx.FXx).

因此我们得到FXx等于f(λx.FXx)x, 这意味着FX是f的传值不动点.

在无法访问亀山和米澤的演算的实现的情况下, 我们可以使用由cupto导出的control来测试这个表达式. 后者是用OCaml实现的. 我们不能测试我们的fix的类型, 因为cupto的类型系统太粗糙了. 然而, 我们可以测试其动态行为. 为了避免传递结果类型有居留元的见证, 我们将结果类型设为a→a, 它显然是有居留元的, 由恒等函数居留.

第11章 通过定界延续得到一般递归类型

一个一般递归类型通常被定义 (参见亀山和米澤) 为μX.F[X], 其中X可能在F[X]中负地 (即逆变地) 出现. 如果X只正地出现 (如同在整数列表的类型μX.(1+Int×X)中那样), 那么所得到的类型常常被称为归纳的.

一个一般递归类型, 例如μX.X→Int→Int, 可以由以下签名刻画:

    module type RecType = sig
     type t     (* abstract *)
     val wrap   : (t->int->int) -> t
     val unwrap : t -> (t->int->int)
    end
只要(unwrap . wrap)是恒等函数. 如果我们有这个签名的一个实现, 我们就可以将诸如λx.xx这样的项从无类型lambda演算转写到有类型lambda演算.

ML支持RecType的一个实现, 使用的是同构递归 (数据) 类型. 然而, 还有另一个实现, 使用的是ML异常. 既然异常是定界控制的一个特殊情形, 我们就得到了带有类似cupto的定界控制的简单类型lambda演算不是强规范化的另一个证明.
