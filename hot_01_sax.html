第1章 引论

编写编译器的关键方面之一在于设计表示源语言和目标语言之间的步骤的合适中间语言. 源语言, 中间语言, 目标语言在整个学期将会逐渐演化, 因为你将会为愈来愈复杂的语言编写一系列编译器. 第一次lab的目标在于让你熟悉中间语言; 第二次lab的目标在于如何转换进和出这种语言.

所有 (或者应该说几乎所有?) 的编译器都依赖于中间语言. 在15-411编译器设计这门课里, 常用的中间语言是静态单赋值 (SSA) 或者LLVM. CMU开发的Standard ML编译器TIL [Tarditi et al., 2004] 使用了多个中间语言, 并且基于这样一个前提: 中间语言应该是有类型的, 一路向下直到有类型汇编语言 (TAL) [Morrisett et al., 2003] 为止.

Sax [DeYoung et al., 2020] 是这个领域中相对较新的成员. 它是相当高层次的, 这是就以下意义而言的: 作为Curry-Howard对应的一个实例, 它对应于一个基于某种形式的相继式演算的逻辑系统. 然而, 它又有着直观的命令式解释. 因为其相对高层次的本性, 定义和使用其亚结构变体是容易的, 探索如何高效地实现这些变体, 以及如何利用它们所保证的性质, 也是容易的.

我们不会一次性展示整个Sax, 而是从一个正的且线性的核心开始. 在这个语境下, 正的意味着语言是一阶的, 也就是说, 它没有任何高阶函数. 而这里的线性意味着不需要传统的垃圾回收, 因为所有的内存单元都可以在被读取时释放.

第2章 正类型与大值

从使用者角度而言, 正类型的值是那些我们可以直接观察结构的值, 其包括布尔值, 自然数, 或者是元素具有可观察类型的列表或树, 等等. 反过来, 负类型的值是那些我们不能直接观察结构但是可以与之进行交互的值, 例如函数和对象.

编程语言理论已经建立了对于类型的构建块的基本理解. 与之对应的是, 证明论也确定了命题的构建块. 我们将几乎完全坚持编程语言的视角, 但是有时会将其和直觉主义(线性)命题联系起来.

我们对大值进行定型的基本判断是 V:A 其表达了大值V具有类型A. 我们所观察的值并不包含任何变量, 因而我们无需使用任何上下文来描述其类型. 之所以我们将这些值称为大的, 是因为一个单独的值就包含了关于计算结果的所有信息.

序对. 对于序对的正类型我们记A⊗B. V:A W:B ( V,W ) : A⊗B ⊗I 这个记号是借用自线性逻辑的, 将规则命名为⊗I以指示这是一条引入规则也是如此. 在直觉主义逻辑中, 这是两种合取形式之一. 在具有按值调用语义的函数式语言 (ML语族) 中, 其被记为A * B, 这也是我们实际所采用的具体句法.

单位. 对于单位类型我们将其记为1, 其中只寓居着单位元素. ( ) :1 1I 在常见的语言中, 单位类型通常记作unit; 在我们的具体句法中就记作1.

和. 对于类型Aℓ的无交和我们记作∑ℓ∈L(ℓ:Aℓ), 其中标签ℓ是从一个有限索引集合L≠{}中取的. 在线性逻辑中, 二元的版本记作A⊕B, 其与直觉主义逻辑中的A∨B是相同的. 为了简单起见, 我们避免了空和. 另外, 因为空和并不包含值, 故其编程应用有限. 我们一般使用ℓ和k代表标签. ( k∈L ) V: Ak k⁡ (V) : ∑ ℓ∈L ( ℓ: Aℓ ) ⊕I V:A inl_ ⁡ (V) : A⊕B ⊕ I1 V:B inr_ ⁡ (V) : A⊕B ⊕ I2 右边我们展示了二元版本这一特殊情形, 其中A⊕B=Δ(inl_:A)+(inr_:B). 它们并非真的是语言的组成部分.

以这些值构造子, 我们已经可以表示诸如布尔(false_:1)+(true_:1)这样的有限类型. 为了表示诸如列表和自然数这样的无限类型, 我们也需要递归.

等价递归类型. 我们没有添加用于构造递归类型的绑定构造子μα.A⁡(α), 而是以顶层定义来表示递归类型, 例如 type nat= ( zero_ :1 ) ⊕ ( succ_ :nat ) {译注: 不要将其与二元和A⊕B混淆, 这个其实是和类型的某种具体句法.} 从现在开始, 我们对于和采用一种更贴近于我们的具体句法的记号. type nat= ⊕ { zero_ :1 , succ_ :nat } 说这些类型是等价递归的是什么意思? 这意味着我们将这种定义视为元层次的等式, 而非需要强制的同构. 下一讲我们将会看到这种简单性是有代价的, 但是我相信这个代价非常值得付出.

因为类型定义是等价递归的, 所以我们有着诸如 succ_ ⁡ ( succ_ ⁡ ( zero_ ⁡ ( ) ) ) :nat 这样的判断. 对于nat这样的类型名称, 我们也没有单独的规则, 因为我们可以悄无声息地应用和的规则来导出以上的判断. ( ) :1 1I zero_ ⁡ ( ) :nat ⊕I succ_ ⁡ ( zero_ ⁡ ( ) ) :nat ⊕I succ_ ⁡ ( succ_ ⁡ ( zero_ ⁡ ( ) ) ) :nat ⊕I 以数学语言, 所有以这种方式定义的正类型都是归纳的. 这需要一个限制: 类型定义的右侧不应该是类型名称本身, 而是应该以某个构造子 (⊗, 1, ⊕) 开始. 这避免了形如typet=t的定义.

此外, 我们允许所有的类型定义都是互递归的, 假如我们使用显式类型构造子μ的话, 这可能会有点令人不快.

作为另一个例子, 自然数的列表可以定义为 type list= ⊕ { nil_ :1 , cons_ : nat⊗list }

第3章 内存和小值

到目前为止我们知道了我们想要表示大值, 但是我们也想要以某种方式在内存中表示大值, 以使得我们能够命令式地对其进行操作. 然而, 一个内存单元不能存放具有任意大小的值, 因而我们需要将大值分解为更小的部分. 我们的方法是使用一种抽象语义对象cellav, 其表示地址a处的内存单元存放着小值v. 一个小值要么是一对地址, 要么是单位值, 要么是一个标签连带着一个地址. 例如, 之前的例子里的数字二可以表示为 cell 0 succ_ ⁡ (1) cell 1 succ_ ⁡ (3) cell 3 zero_ ⁡ (4) cell 4 ( ) 这里我们用了整数来表示地址, 这对于真实内存而言实际上是典型的. 我们也假定了每个内存单元都有足够的空间用于存放任意的小值. 通常来说, 两个机器字就足以存放一对地址, 带标签的值, 以及单位值.

我们或许已经可以预见到这里的一些优化, 例如不分配一个显式的单元来存放单位值. 然而, 重要的是在这个阶段不要沉迷于这些考虑, 而是先实现直接的版本. 一方面, 它是有理论支撑的, 并且其实现应该是简单的, 因而比一个更复杂但可能经过优化的实现更有可能是正确的. 另一方面, 它为我们提供了一个基线, 使得我们之后可以测量优化实际上给我们带来了什么.

还有一点: 程序可被观察到的结果是它的大值, 而不是它精确的布局. 在上面的例子中, 我们跳过了地址2, 就是为了说明这一点. 因此, 在求值结束时, 需要一个小程序来遍历内存并打印出大值. 这个程序将依赖于对于内存布局的特定选择, 例如单位值是否被显式表示.

第4章 对于内存进行定型

我们如何给一个内存单元指派类型呢? 例如, 单元 cellc ( a,b ) 定义了地址c处的小值, 并引用了地址a和b处的小值. 因此, 我们将其定型为 a:A , b:B ⊢ cellc ( a,b ) :: ( c: A⊗B ) 这与大值的定型有两处不同. 一是现在有了代表其他内存单元 (这里是a和b) 的类型的前件. 二是我们也为后件提供了一个地址 (这里是c), 以追踪小值存放在何处.

一般而言, 我们希望在程序执行时维持类型——这是一个几乎普适的原则, 用以确保计算的结果满足关于其类型的原初期望. 因此, 一个写入内存单元的命令应该恰以结果单元的方式被定型. 这给出了以下规则. a:A , b:B ⊢ writec ( a,b ) :: ( c: A⊗B ) ⊗X ·⊢ writec ( ) :: ( c:1 ) 1X ( k∈L ) a: Ak ⊢ writec k⁡ (a) :: ( c: ∑ ℓ∈L ( ℓ: Aℓ ) ) ⊕X 我们将它们命名为X是因为如果忽略命令的话, 它们代表了逻辑公理. A,B ⊢ A⊗B ⊗X ·⊢1 1X A⊢ A⊕B ⊕ X1 B⊢ A⊕B ⊕ X2 于是这些规则保持了与逻辑规则的对应. 定型判断现在具有形式 a1 : A1 ,…, an : An ⏟ 从这里读取 ⊢ P:: ( c:C ) ⏟ 写入这里 其中a1,…,an和c代表地址, 而P是一个要执行的命令. 我们常常将P视为一个进程, 因为 (正如我们将会看到的) 这个语言有着自然的并行解释. 如果我们想要强调顺序意义, 我们就说命令.

在我们的动态语义中, 语义对象有两种形式. cellcv表示地址为c的单元存放着小值v. 我们也记procP, 其意味着进程P正在执行. 于是, 写操作的动态语义的规定几乎是平凡的: proc ( writecv ) ⟶ cellcv

第5章 从内存中读取

将小值写入内存很容易借由内存单元本身必须如何定型来解释. 那么读取呢? 例如, 当读取一个序对时, 我们将两个变量绑定到地址, 一个绑定到第一个分量, 另一个绑定到第二个分量. 相应的构造是 readc ( x,y ) ⇒ P⁡ ( x,y ) 其中我们显式写出了P对于x和y的依赖.

我们可以看到, 如果c:A⊗B存放着一个小值(a,b), 那么在我们执行P时, x应该被绑定到a, y应该被绑定到b. 我们将其记为 cellc ( a,b ) , proc ( readc ( x,y ) ⇒ P⁡ ( x,y ) ) ⟶ proc P⁡ ( a,b ) 这对于定型意味着什么呢? 当我们从c读取时, 我们使用了它, 然后在给P定型时我们就可以使用a和b (在程序中由x和y表示). Γ, x:A , y:B ⊢ P⁡ ( x,y ) ::δ Γ, c: A⊗B ⊢ readc ( x,y ) ⇒ P⁡ ( x,y ) ::δ ⊗L 这里, 我们用δ表示诸如d:D这样的东西, 它命名了P最终必须写入的地址. 我们常常将d称为目的地.

单位类型的情况是类似的, 但是并不绑定任何变量. cellc ( ) , proc ( readc ( ) ⇒P ) ⟶ procP 而从定型的角度来看: Γ⊢ P::δ Γ, c:1 ⊢ readc ( ) ⇒P ::δ 1L

为了读取和, 进程必须考虑所有可能的和项. ( Γ, xℓ : Aℓ ⊢ Pℓ ⁡ ( xℓ ) ::δ ) ( ∀ ℓ∈L ) Γ, c: ∑ ℓ∈L ( ℓ: Aℓ ) ⊢ readc { ℓ⁡ ( xℓ ) ⇒ Pℓ ⁡ ( xℓ ) } ℓ∈L ::δ ⊕L ⊕L规则对于L中的每个标签都有一个前提, 因此在命令执行期间正确的分支总是可用的. cellc k⁡ (a) , proc ( readc { ℓ⁡ ( xℓ ) ⇒ Pℓ ⁡ ( xℓ ) } ℓ∈L ) ⟶ proc Pk ⁡ (a) ( k∈L )

这些规则被称为左规则, 因为它们考虑的是前件的类型, 也就是说, 位于十字转门左侧的东西. 它们就是Gentzen的相继式演算 [Gentzen, 1935] 中的左规则, 读者可能对此有所了解. Γ,A,B ⊢C Γ, A⊗B ⊢C ⊗L Γ⊢C Γ,1 ⊢C 1L Γ,A ⊢C Γ,B ⊢C Γ, A⊕B ⊢C ⊕L 我们观察到, 从逻辑的角度来看, 我们保留了相继式演算的所有左规则, 而将右规则替换为了公理. 这就是为什么我们称其为半公理相继式演算 (semi-axiomatic sequent calculus), 简称Sax.

第6章 切和恒等

我们还缺少相继式演算中的两条重要规则, 即切和恒等. Γ⊢A Δ,A ⊢C Γ,Δ ⊢C cut A⊢A id 它们在这里是什么意思呢? 原来, 切分配了一个新鲜的内存单元. Γ⊢ P⁡ (x) :: ( x:A ) Δ, x:A ⊢ Q⁡ (x) ::δ Γ,Δ ⊢ cut ( x:A ) P⁡ (x) Q⁡ (x) ::δ cut 我们既可以将其读作一个并行构造, 也可以将其读作一个顺序构造, 后者是并行程序的一种特定调度. 进程 cut ( x:A ) P⁡ (x) Q⁡ (x) 分配一个新的单元a (在程序中以x指称) {译注: 原文此处写作referred to as a in the program, 应为笔误.} 并派生一个进程P⁡(a), 其职责是写入a. 进程Q⁡(a)将会从a读取. 我们的定型判断的解释在这里并没有留下多少余地. 注意a被称为一个期值 (future) [Halstead, 1985, Pruiksma and Pfenning, 2022], 也是一个同步点: 如果Q⁡(a)试图在P⁡(a)写入a之前从a读取, 那么Q⁡(a)将会阻塞, 直到a被写入.

顺序解释完整地执行P⁡(a) (也就是说, 直到它写入其目的地a为止), 然后才执行Q⁡(a). 于是, Q⁡(a)永远无需检查a是否已经被写入, 因为它保证已经被写入了.

从动态语义的角度来看, 它不过就是 proc ( cut ( x:A ) P⁡ (x) Q⁡ (x) ) ⟶ proc P⁡ (a) , proc Q⁡ (a) ( a 新鲜 )

我们看到, 在动态语义的这种表述中, 状态里可以有不止一个proc对象. 抽象规则允许其中任何有可应用规则的对象进行转移. 当然, 存在一些方法可以形式化地强制procP⁡(a)在procQ⁡(a)开始之前完成, 但是如果我们的关键性质 (例如标准的进展和保持) 并不依赖于此, 我们也可以让它保持非形式化. 某种程度上说, 任何与规则相容的策略对于实现而言都是允许的.

这种规定动态语义的方式被称为亚结构操作语义 (substructural operational semantics, SSOS) [Pfenning, 2004, Pfenning and Simmons, 2009, Simmons, 2012], 它基于多重集重写 [Cervesato and Scedrov, 2009], 因为构成计算状态的语义对象的汇集被解释为一个多重集. 关于这一点, 下一讲会讲更多.

恒等规则只是通过在一步之内从一个单元读取并写入另一个单元, 将一个小值从一个单元移动到另一个单元. b:A ⊢ idab :: ( a:A ) id 其动态语义为 cellbv , proc ( idab ) ⟶ cellav

第7章 过程定义

到目前为止, 我们的语言只有正类型, 那么如何可能定义过程呢? (我们说过程, 是因为执行它们是为了其对于存储的效应, 而不像函数那样接受一个参数并返回一个结果.) 我们在课上没有讨论这一点, 但是我们在现场编写的例子中用到了它.

这一点有些重要, 因为我们想要在允许第一级函数, 对象等之前定义一个一阶语言. 为了定义一个名为p的过程, 我们写 procp ( x:A ) ( y1 : B1 ) … ( yn : Bn ) = P⁡ ( x, y1 ,…, yn )

每个过程p首先接受一个目的地 (这里是x:A), 然后是额外的参数yi. 在执行时, x和所有的yi都将被绑定到地址. 为了实现这一点, 我们有一个新的构造 callpa b1 … bn 其中参数的数目, 位置和类型必须与过程定义中的那些相匹配.

就像类型定义那样, 过程定义可以是任意互递归的. 这与诸如Standard ML和OCaml这样的语言中以句法方式表达的(互)递归形式不同.

我们已经说过过程不是函数, 那么它们是什么呢? 原来, 它们是上下文模态类型论 [Nanevski et al., 2008] 意义下的元变量. 考虑对于某个元变量p的相继式 y1 : B1 ,…, yn : Bn ⊢ p:: ( x:A ) p的类型是什么? 它既依赖于所有的前件, 也依赖于后件. 在上下文模态类型论中, 我们可能会写 p:: A [ y1 : B1 ,…, yn : Bn ] 但是这里目的地x也必须被命名, 因此它也许可以写成 p:: ( y1 : B1 ,…, yn : Bn ⊢ x:A ) 因此, p代表的是整个相继式的推导, 而不是诸如B→A这样的单个函数. 此外, p将是闭的, 意思是它的所有变量都将是x和yi, 而没有其他东西. 正是这种闭的性质, 使得即便类型系统在其他方面是线性的, 我们也可以任意地重用这些过程定义.

我们将在下一讲中处理过程定义和调用的定型.

第8章 一些示例代码

在具体句法中有一些选择要做. 我们将⊕简单地写成+, 将⊗写成*. 此外, 所有的标签都具有形式'<ident>. 注释具有形式// ...\n或/* ... */, 后者可以正确地嵌套. 另外, read的分支被括在花括号{ ... }中, 并且每个选项前面都有一条竖线|. 唯一的例外是只有单个分支的情况. 更多细节可以在Lab 1的规范中找到, 我们在课上现场编写了这些代码.

尽管句法本身使其无歧义, 我们还是使用缩进将写入新分配单元的命令与读取者区分开来. 下面的文件是lec01.sax.

/* Lecture 1 */
/* 15-{4,6,8}17 Spring 2025 */

type nat = +{'zero : 1, 'succ : nat}

type bin = +{'b0 : bin, 'b1 : bin, 'e : 1}

// two = 'b0 'b1 'e ()

proc zero (d : bin) =
  cut u : 1
    write u ()
  write d 'e(u)

proc one (d : bin) =
  cut x : bin
    call zero x
  write d 'b1(x)

proc succ (d : bin) (x : bin) =
  read x {
  | 'b0(x0) => write d 'b1(x0)
  | 'b1(x1) => cut y : bin
                  call succ y x1
               write d 'b0(y)
  | 'e(u) => read u ()
             call one d
  }

proc two (d : bin) =
  cut x : bin
    call one x
  call succ d x

无参数过程 (那些只有一个目的地的过程) 可以被执行, 这里就是zero, one和two. 它们产生一个终态, 从中可以读出相应大值的表示. 相应的文件lec01.sax.val由编译器写出, 其内容如下.

value zero = 'e ()
value one = 'b1 'e ()
value two = 'b0 'b1 'e ()

第9章 总结
