逻辑关系

第1章 引论

逻辑关系是一种多产且极为有用的证明方法, 可用于证明程序和语言的各种性质. 例如, 逻辑关系可以帮助证明:

  • 诸如简单类型lambda演算 (STLC) 这样的语言中的良类型程序的终止性;
  • 诸如STLC这样的语言的类型可靠性/安全性;
  • 程序等价性, 其形式多样:
    • 验证经过优化的算法或实现等价于更简单的朴素算法或实现;
    • 论证编译器优化或变换的正确性;
    • 表明表示独立性 [Mit86], 即某一接口背后的实现不会影响客户端的行为;
      • 例如, 栈接口可以用数组或链表来实现, 但这对于接口的使用者而言应当是不可区分的. 为了证明栈接口的表示独立性, 我们需要证明使用数组实现的程序与使用链表实现的程序是等价的.
    • 将参数化多态性及其对应的自由定理 [Wad89] 概念化为一种关系, 大致描述为相关的输入映射到相关的输出;
    • Proving noninterference for security-typed languages: showing that two runs of a given program are equivalent on low-security outputs for any variation on high-security (e.g. confidentiality) program data;
  • 以及更多!

近期研究中, 逻辑关系已被用于证明不同逻辑的可靠性. 跨语言逻辑关系则用于推理编译过程, 外部函数接口或多语言语义.

逻辑谓词与一元逻辑关系这两个术语是同义的, 逻辑关系与二元逻辑关系亦然. 这两种术语在文献和日常用语中均有使用. 逻辑谓词Pτ⁡(e)是集合, 用于对单个程序进行推理. 程序终止性, 类型安全性与可靠性均属于逻辑谓词. 而逻辑关系Rτ⁡(e1,e2)是二元关系, 可用于更广泛地刻画程序等价性.

第2.2节 第一次尝试: 以定型推导上的归纳证明STLC是规范化的

为了看明白为什么我们想要使用逻辑关系, 让我们先尝试朴素地证明第2.1节里的这个规范化定理, 并理解我们卡在了哪里.

证明. 设⋅⊢e:τ, 欲证明e⇓. 我们以定型推导上的归纳进行处理:
  • T-True情形: ⋅⊢ true:bool true已经是一个值了, 所以终止.
  • T-False情形: ⋅⊢ false:bool false已经是一个值了, 所以终止.
  • T-Var情形: Γ⁡ (x) =τ Γ⊢ x:τ 根据归纳假设, 我们得到了⋅⁡(x)=τ, 这意味着该情形空虚为真, 鉴于我们的上下文为空. {译注: 不如说是并不适用于此情形.}
  • T-Abs情形: Γ, x: τ1 ⊢ e: τ2 Γ⊢ λ x: τ1 .e : τ1 → τ2 λx:τ1.e已经是一个值了, 所以终止.
  • T-If情形: Γ⊢ e:bool Γ⊢ e1 :τ Γ⊢ e2 :τ Γ⊢ ifethen e1 else e2 :τ 根据归纳假设, 我们知道e⇓,e1⇓,e2⇓. 既然对于某个v有e⇓v, 通过检视我们的归约语义, 我们知道ifethene1elsee2↦⁎ifvthene1elsee2. 感谢canonical form引理, 我们知道具有类型bool的值只能是true和false. 根据v上的情形分析, 要么ifethene1elsee2↦⁎iftruethene1elsee2↦⁎e1↦⁎v1, 要么ifethene1elsee2↦⁎iffalsethene1elsee2↦⁎e2↦⁎v2.
  • T-App情形: Γ⊢ e1 : τ2 → τ1 Γ⊢ e2 : τ2 Γ⊢ e1 e2 : τ1 根据归纳假设, 我们知道e1⇓和e2⇓v2. 类型为τ2→τ1的值是lambda表达式, 故e1⇓λx:τ2.e′, 于是e1e2↦⁎(λx:τ2.e′)e2↦⁎e′[v2/x]. 问题来了, 我们对于e′[v2/x]的情况一无所知, 于是证明就卡住了.
◻

我们这里主要的insight在于, 归纳假设太弱了: 定型判断没有告诉我们关于规范化所产生的值的任何信息. 为了解决这个问题, 我们将会定义一个逻辑关系, 其精确地加强了归纳假设, 这允许我们知道关于求值所产生的值的更多信息.

第2.3节 定义逻辑关系的原则

逻辑关系是表达式上的谓词Pτ⁡(e), 由类型索引. 在定义一个逻辑关系时, 通常我们需要遵循三条原则:

  • 逻辑关系应包含良类型的项, 这里即⋅⊢e:τ;
  • 我们所关心的性质P应当内嵌于逻辑关系之中, 这里即规范化;
  • 我们所关心的性质应当在相应类型τ的消去形式下得到保持. 从直觉上来说, 这意味着我们有方法在消费了类型为τ的值之后继续.
接下来我们将会看到如何具体构造逻辑关系以证明STLC是规范化的.

第2.4节 STLC规范化的逻辑关系

我们根据STLC类型上的归纳定义规范化的逻辑谓词, 遵循之前提及的三条原则: Nbool ⁡ (e) =def ⋅⊢ e:bool ∧ e⇓ N τ1 → τ2 ⁡ (e) =def ⋅⊢ e: τ1 → τ2 ∧ e⇓ ∧ ∀ e′ . N τ1 ⁡ ( e′ ) ⟹ N τ2 ⁡ ( e e′ ) 与前述原则相比较, 我们可以看出, 两种情况下最左边的合取分量都确保了逻辑关系中只包含良类型的项. 类似地, 两种情况下的下一个合取分量确保了逻辑关系中只包含满足所需性质 (即规范化) 的项. 最后, 我们需要确保所关注的性质在消去形式下得以保持, 这一点由τ1→τ2情况中的第三个合取分量来处理. 有趣的是, 我们无需对bool的消去形式作任何说明, 这是由其正极性所决定的. 作为一条经验法则, 具有正极性的类型不需要任何额外的合取分量, 而具有负极性的类型则需要.

由此出发, 我们可以将规范化的证明拆分为两个步骤:

  1. 对于所有的项e, 如果⋅⊢e:τ, 那么Nτ⁡(e);
  2. 对于所有的项e, 如果Nτ⁡(e), 那么e⇓.

步骤B可以直接由逻辑谓词Nτ的定义推出. 根据τ上的归纳, 我们有两种需要考虑的情形, 而每种情形下e⇓都可以直接由Nτ⁡(e)的定义得到. 我们或许可以评注一下, 这实际上来源于第二条原则: 我们关心的性质 (规范化) 就在逻辑关系的定义之中.

然而, 由于lambda抽象的问题, 步骤A并不如此直接. 设⋅⊢λx:τ1.e:τ1→τ2, 于是我们知道x:τ1⊢e:τ2. 为了证明A, 我们需要表明⋅⊢λx:τ1.e:τ1→τ2, 这由假设成立. 我们也必须表明λx:τ1.e⇓, 这之所以成立, 是因为lambda项已然为值. 最后的一步是要证明对于任意的项e′, 如果Nτ1⁡(e′), 那么Nτ2⁡((λx:τ1.e)e′). 此时我们卡住了, 因为e不是一个封闭项, 于是我们不能通过定型推导上的归纳进行处理.

第4.1节 递归类型的目的

递归类型可以捕获潜在无限的数据结构, 例如列表, 流, 树, 等等. 加入递归类型到语言里允许非终止程序通过类型检查.

为了刻画递归类型的用处, 让我们检视无类型lambda演算里的Ω组合子, 其无限循环: Ω= ( λx. xx ) ( λx. xx )

如果我们试着将第一个项应用于第二个项, 我们就又步入了Ω组合子. 现在让我们试着在简单类型lambda演算中对于该项进行定型: Ω= ( λ x:? . xx ) ( λ x:? . xx )

x的一个面貌是其在项(λx.xx)中被应用于自身, 所以我们期望其类型差不多是τ1→τ2. 然而, 作为函数x的参数的x的类型就不大对了. 我们将会看到递归类型是如何帮助对于Ω组合子进行定型的.
