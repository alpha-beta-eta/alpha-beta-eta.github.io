可扩展指称语义, 现代重述

本文是对Robert Cartwright和Matthias Felleisen的论文Extensible Denotational Language Specifications (TACS 1994) 的一个重述. 原文的译文见可扩展指称性语言描述. 原文的思想至今仍然新鲜, 但它的记号 (粉碎积, 合并和, 提升) 和代码 (Rice Scheme的第一级模块) 都已经很难读了. 这里我们用一个可以在Racket 9上运行的实现为线索, 从头讲一遍这个故事, 并尽量使用今天的程序员熟悉的记号. 文中的每个公式都直接对应一段代码, 读者可以对照着读.

记号约定

本文的公式中, 字体是有含义的:

  • 等宽字体表示对象语言 (即被定义的语言) 的句法, 例如(add1e), (ife1e2e3), 以及数码5. 数码5是句法, 而5是它所表示的整数. 唯一的例外是λ: 我们把抽象写成(λ(x)e), 而在程序文本中它写作lambda. 黑底白字只用于Racket代码, 例如arith-mixin.
  • 斜体表示元变量 (metavariable), 并且我们固定以下用法: e是表达式, x是变量, n是整数, v,a是值, c是计算, k是句柄, κ是延续, f,g是函数, ρ是环境, σ是存储, r是资源, ℓ是位置, m是错误说明.
  • 无衬线的直立字体表示语义构造子, 即值, 计算和动作的各种形状, 例如Val, FX, Num, Ref. 它们与实现中的Racket结构体同名, 例如Num⁡(5)对应实现中的(Num 5).
  • 普通的直立字体表示元语言中的函数, 例如admin, ask, err.
  • 粗体表示元语言的关键字, 本文只用到case和of.
此外还有以下记号:
  • ⟦e⟧ρ是表达式e在环境ρ中的含义, ρ[x↦v]是把x绑定到v之后得到的环境; σ[ℓ↦v]同理.
  • λx.e是元语言中的匿名函数, f⁡(x)是函数应用, (v,r)是序对.
  • casexofp⇒e|…按x的形状分情形; _匹配任何东西.
  • x⇐c;e是顺序组合, 定义见第3.2节.
  • 我们不使用domain理论: 集合与函数按通常的意思理解, ⊥表示发散. 原文中的严格性, 提升等细节对本文的论述并不重要.

第1章 问题: 数码5指称什么?

指称语义给每个程序句法成分指派一个数学对象. 最简单的句法成分莫过于数码5. 然而它的指称取决于语言的其余部分: 纯函数式语言 ⟦5⟧ ρ =5 ⟦5⟧ : Env→V 加上引用单元 ⟦5⟧ ρσ = ( 5,σ ) ⟦5⟧ : Env→Sto→ ( V×Sto ) 再加上延续 ⟦5⟧ ρκσ = κ5σ ⟦5⟧ : Env→ ( V→Sto→Ans ) →Sto→Ans 每向语言添加一种效应, 所有已有的子句都要重写一遍, 包括那些与新效应毫无关系的子句, 例如数码的子句. 更糟糕的是, 程序员在推理一段纯函数式代码时, 心里想的明明是第一行的简单含义, 但语言的正式定义给的却是第三行; 要从后者中恢复前者, 就必须证明一个不平凡的定理.

本文的目标是给出一种指称语义的写法, 在这种写法中 ⟦5⟧ ρ = Val⁡ ( Num⁡ (5) ) 在每一个扩展中都成立, 并且添加一种新的语言构造只需要添加新的定义, 而不需要修改任何旧的定义.

第2章 直觉: 进程与内核

设想一个操作系统. 进程自己做算术, 自己调用函数; 但它不能自己去读写磁盘, 而是发出一个系统调用, 把控制权交给内核. 内核完成请求之后, 再把结果交还给进程, 让它从中断处继续.

扩展直接语义 (extended direct semantics) 就是这样组织一个语言的. 程序的每个句法成分的含义是一个计算 (computation), 它要么是一个值, 要么是一个请求. 请求由两部分组成:

  • 一个动作 (action), 说明要求做什么, 例如 分配一个存有7的单元;
  • 一个句柄 (handle), 即得到回复之后的其余计算, 它是一个从值到计算的函数.
所有的全局资源 (例如存储) 都只归一个中央管理者admin所有. 句法成分之间不传递存储, 也不传递延续; 只有管理者知道它们.

这一想法来自操作语义. 在带引用单元的λ演算中, 表达式 E [ ( refv ) ] 不能被局部地归约: 分配一个新单元必须知道整个存储. 但我们可以把它看作一条消息: (refv) 是请求, 求值上下文E就是句柄. 管理者分配一个新位置ℓ, 然后用ℓ填充E的洞, 计算继续进行. 下面的定义只是把这幅图景翻译成函数.

第3章 框架

第3.1节 计算

设V是值的集合, A是动作的集合 (两者都依赖于语言, 是可扩展的). 计算的集合C由以下两种形状组成: C ⩴ Val⁡ (v) 一个值, 其中 v∈V | FX⁡ ( k,a ) 一个请求, 其中 a∈A , k: V→C 这就是框架的全部. 数, 过程, 位置, 延续等等都是V的扩展; 错误, 分配, 读写, 控制转移等等都是A的扩展. C本身的定义永远不变.

我们给两个常用的构造起名字: ask⁡ (a) ≔ FX⁡ ( Val,a ) err⁡ (m) ≔ ask⁡ ( Exc⁡ (m) ) ask发出一个动作, 并且约定把管理者的回复直接当作值; Exc⁡(m)是唯一一个所有语言都有的动作: 带着说明m的错误. 说明只是为了调试方便, 下文的公式中我们省略它, 只写err.

图3.1.1. [计算 (framework.rkt)]
(struct Val (v))            ; a value
(struct FX (k action))      ; a request: handle k and an action
(struct Exc (msg))          ; the action: error

(define inVal Val)
(define (inAC action) (FX inVal action))   ; i.e. ask
(define (inExc msg) (inAC (Exc msg)))      ; i.e. err

第3.2节 顺序组合

一个复合句法成分需要先计算它的子句法成分. 如果子计算给出一个值, 就在局部用掉它; 如果给出一个请求, 就必须把它原样上交, 只是在句柄的末尾接上 拿到值之后我还要做的事. 我们把这一操作写成 x⇐c; e 读作 令x为c的值, 然后计算e. 它由下面两个方程定义: x⇐ Val⁡ (v) ; e = e [ x↦v ] x⇐ FX⁡ ( k,a ) ; e = FX⁡ ( λy. x⇐ k⁡ (y) ; e ,a ) 第一个方程说值被直接交给e; 第二个方程说请求向上传播, 并且它的句柄被扩大了. 一个请求就这样一层一层地向外传播, 最终抵达管理者; 而它携带的句柄恰好就是整个程序的其余部分.

熟悉Haskell的读者会认出, x⇐c;e就是do记号, 而C连同这一操作构成一个单子. 确切地说, C是动作的自由单子 (free monad): 它对动作本身什么也不解释, 只是忠实地把它们记录下来. 解释动作是管理者的事.

图3.2.1. [顺序组合 (framework.rkt)]
(define (handle comp consumer)
  (match comp
    [(Val v)    (consumer v)]
    [(FX k act) (FX (lambda (x) (handle (k x) consumer)) act)]))

;; (handle* ([f c1] [a c2]) body)
;;   = (handle c1 (lambda (f) (handle c2 (lambda (a) body))))
(define-syntax handle*
  (syntax-rules ()
    [(_ () body ...) (let () body ...)]
    [(_ ([x comp] more ...) body ...)
     (handle comp (lambda (x) (handle* (more ...) body ...)))]))

第3.3节 管理者与程序的含义

管理者admin接受一个计算和当前的资源r, 返回程序的最终答案: 一个值 (或错误) 连同最终的资源. 对于不带任何资源的基础语言, 它只有两个子句: admin⁡ ( Val⁡ (v) ,r ) = ( v,r ) admin⁡ ( FX⁡ ( k, Exc⁡ (m) ) ,r ) = ( err⁡ (m) ,r ) 注意错误的句柄k被直接丢弃了: 这就是中止程序. 程序P的含义是解释器与管理者的复合: ⟦P⟧ = admin⁡ ( ⟦P⟧ ∅ , r0 ) , 其中r0是初始资源. 基础语言只有两个程序: 发散的loop和报错的err: ⟦loop⟧ ρ = ⊥ ⟦err⟧ ρ = err 任何真正的语言都是这个平凡语言的扩展.

第3.4节 扩展的形状

一个语言片段 (language fragment) 由以下六部分组成, 每一部分都只是添加而不是修改:

  1. 新的句法形式;
  2. 新的值, 即V的新形状;
  3. 新的动作, 即A的新形状;
  4. 新的资源;
  5. 解释器⟦⋅⟧的新子句, 每个新句法形式一个;
  6. 管理者admin的新子句, 每个新动作一个.
下一章依次给出算术, λ演算, 布尔值, 引用单元和延续这五个片段. 它们都具有同样的形状; 读者读完前两个之后, 其余的大概可以自己写出来.

第4章 语言片段

第4.1节 算术

这个片段添加数码和两个算术运算, 以及一种新的值, 整数: e ⩴ n| ( add1e ) | ( sub1e ) V ⩴ …| Num⁡ (n) n∈ℤ 其中V的定义里的…表示其他片段添加的形状. 解释器的新子句是 ⟦n⟧ ρ = Val⁡ ( Num⁡ (n) ) ⟦ ( add1e ) ⟧ ρ = x⇐ ⟦e⟧ ρ ; casexof | Num⁡ (n) ⇒ Val⁡ ( Num⁡ ( n+1 ) ) |_⇒err

这正是我们在第一章许诺的: 数码的含义是Val⁡(Num⁡(n)), 其中没有存储, 也没有延续. (add1e)先计算e, 如果得到一个数就加一, 否则报错. (sub1e)同理. 算术片段没有新的动作, 也没有新的资源, 因而不需要修改管理者.

图4.1.1. [算术片段 (arith.rkt)]
;; syntax
(struct Int (n))
(struct Add1 (e))
(struct Sub1 (e))
;; new value
(struct Num (n))

(define arith-mixin
  (mixin (language<%>) ()
    (super-new)
    (define/override (interpret exp env)
      (match exp
        [(Int n)  (inVal (Num n))]
        [(Add1 e) (handle (interpret e env) (op add1))]
        [(Sub1 e) (handle (interpret e env) (op sub1))]
        [_ (super interpret exp env)]))))

(define ((op f) v)
  (match v
    [(Num n) (inVal (Num (f n)))]
    [_ (inExc "not a number")]))

代码中的mixin, super等等将在第5章解释; 现在只需知道, (interpret e env)是对完整语言的解释器的递归调用, 而(super interpret exp env)把本片段不认识的句法交给之前的语言.

第4.2节 传值λ演算

这个片段添加变量, 抽象和应用, 以及一种新的值, 过程: e ⩴ x| ( λ (x) e ) | ( e1 e2 ) V ⩴ …| Proc⁡ (f) f: V→C 解释器的新子句是 ⟦x⟧ ρ = Val⁡ ( ρ⁡ (x) ) ⟦ ( λ (x) e ) ⟧ ρ = Val⁡ ( Proc⁡ ( λv. ⟦e⟧ ρ [ x↦v ] ) ) ⟦ ( e1 e2 ) ⟧ ρ = f⇐ ⟦ e1 ⟧ ρ ; a⇐ ⟦ e2 ⟧ ρ ; casefof | Proc⁡ (g) ⇒ g⁡ (a) |_⇒err

过程的指称是一个从值到计算的函数, 因为过程体可能发出请求. 应用(e1e2)从左到右计算算子和实参, 这正是⇐在这里规定的求值顺序. 这个片段同样不需要新的动作或资源.

有了这两个片段我们已经得到了一个函数式语言. 注意它的解释器是一个直接语义: 环境是唯一的额外参数, 没有存储, 也没有延续. 如果从来没有请求发生 (除了错误), ⇐就退化为普通的let, 而整个定义就是教科书上的直接语义.

图4.2.1. [传值λ演算片段 (cbv.rkt)]
;; syntax
(struct Var (x))
(struct Lam (x body))
(struct App (rator rand))
;; new value
(struct Proc (f))

(define cbv-mixin
  (mixin (language<%>) ()
    (super-new)
    (define/override (interpret exp env)
      (match exp
        [(Var x) (inVal (lookup env x))]
        [(Lam x body)
         (inVal (Proc (lambda (v) (interpret body (extend env x v)))))]
        [(App e1 e2)
         (handle* ([f (interpret e1 env)]
                   [a (interpret e2 env)])
           (match f
             [(Proc g) (g a)]
             [_ (inExc "not a procedure")]))]
        [_ (super interpret exp env)]))))

第4.3节 布尔值

原文的代码因篇幅原因省略了这个片段, 但没有它就写不出递归程序. 它与算术片段如出一辙: e ⩴ #t|#f| ( if e1 e2 e3 ) | ( zero?e ) V ⩴ …| Truth⁡ (b) b∈ { #t,#f } ⟦ ( if e1 e2 e3 ) ⟧ ρ = t⇐ ⟦ e1 ⟧ ρ ; casetof | Truth⁡ (#t) ⇒ ⟦ e2 ⟧ ρ | Truth⁡ (#f) ⇒ ⟦ e3 ⟧ ρ |_⇒err (zero?e)的子句留给读者. 至此我们得到了原文的Pure Scheme. 用Z组合子可以写出递归函数. 下面在Racket中用run运行一个加法的例子:

(define Z
  '(lambda (f)
     ((lambda (x) (f (lambda (v) ((x x) v))))
      (lambda (x) (f (lambda (v) ((x x) v)))))))

(run `(((,Z (lambda (add)
              (lambda (m)
                (lambda (n)
                  (if (zero? m) n (add1 ((add (sub1 m)) n)))))))
        20)
       22))
;; => (answer (Num 42) ...)

第4.4节 引用单元

现在来到第一个真正的效应. 存储是全局资源, 因此句法成分不能自己读写存储, 只能请求管理者代劳. 于是这个片段除了新的句法和新的值, 还添加了三个动作: e ⩴ ( refe ) | ( derefe ) | ( setref! e1 e2 ) V ⩴ …| Loc⁡ (ℓ) ℓ∈ℕ A ⩴ …| Ref⁡ (v) | Der⁡ (ℓ) | Set⁡ ( ℓ,v ) 以及一种新的资源: 存储σ:ℕ⇴V, 即有限的从位置到值的映射. 解释器的新子句只是把请求发出去: ⟦ ( refe ) ⟧ ρ = v⇐ ⟦e⟧ ρ ; ask⁡ ( Ref⁡ (v) ) ⟦ ( derefe ) ⟧ ρ = l⇐ ⟦e⟧ ρ ; caselof | Loc⁡ (ℓ) ⇒ ask⁡ ( Der⁡ (ℓ) ) |_⇒err ⟦ ( setref! e1 e2 ) ⟧ ρ = l⇐ ⟦ e1 ⟧ ρ ; v⇐ ⟦ e2 ⟧ ρ ; caselof | Loc⁡ (ℓ) ⇒ ask⁡ ( Set⁡ ( ℓ,v ) ) |_⇒err 真正的工作由管理者完成: admin⁡ ( FX⁡ ( k, Ref⁡ (v) ) ,σ ) = admin⁡ ( k⁡ ( Loc⁡ (ℓ) ) , σ [ ℓ↦v ] ) ,其中 ℓ= |σ| admin⁡ ( FX⁡ ( k, Der⁡ (ℓ) ) ,σ ) = admin⁡ ( k⁡ ( σ⁡ (ℓ) ) ,σ ) admin⁡ ( FX⁡ ( k, Set⁡ ( ℓ,v ) ) ,σ ) = admin⁡ ( k⁡ ( Loc⁡ (ℓ) ) , σ [ ℓ↦v ] ) 为简洁起见, 这里只写出了资源中的存储分量σ; 实现中资源是一张表, 存储是其中名为'store的一项, 其他片段可以往表中添加别的资源而互不干扰. |σ|是存储中已有位置的个数; 位置从不回收, 因此它总是一个新位置.

对比引言中的第二行: 那里每个子句都要接收和返回存储, 而这里只有管理者的三个子句提到了存储. 算术片段和λ演算片段的子句一个字也没有改.

让我们跟踪一个小例子 (deref(ref7)). 解释器给出 ⟦ ( ref7 ) ⟧ ρ = ask⁡ ( Ref⁡ ( Num⁡ (7) ) ) ⟦ ( deref ( ref7 ) ) ⟧ ρ = FX⁡ ( k, Ref⁡ ( Num⁡ (7) ) ) 其中k= λl. caselof Loc⁡ (ℓ) ⇒ ask⁡ ( Der⁡ (ℓ) ) |… 也就是说, 整个程序的含义是一个分配请求, 其句柄是拿到位置之后去读它. 管理者接着处理它: admin⁡ ( FX⁡ ( k, Ref⁡ ( Num⁡ (7) ) ) ,∅ ) = admin⁡ ( k⁡ ( Loc⁡ (0) ) , { 0↦ Num⁡ (7) } ) = admin⁡ ( FX⁡ ( Val, Der⁡ (0) ) , { 0↦ Num⁡ (7) } ) = admin⁡ ( Val⁡ ( Num⁡ (7) ) , { 0↦ Num⁡ (7) } ) = ( Num⁡ (7) , { 0↦ Num⁡ (7) } ) 程序与管理者交换了两次消息: 一次分配, 一次读取.

图4.4.1. [引用单元片段的管理者 (store.rkt)]
(define/override (admin comp resources)
  (define store (hash-ref resources 'store))
  (define (with-store s) (hash-set resources 'store s))
  (match comp
    [(FX k (Ref v))
     (define l (hash-count store))             ; a fresh location
     (admin (k (Loc l)) (with-store (hash-set store l v)))]
    [(FX k (Der l))
     (admin (k (hash-ref store l)) resources)]
    [(FX k (Set l v))
     (admin (k (Loc l)) (with-store (hash-set store l v)))]
    [_ (super admin comp resources)]))

(define/override (initial-resources)
  (hash-set (super initial-resources) 'store (hasheqv)))

注意管理者的每个子句在执行完动作之后都调用admin本身, 即完整语言的管理者, 因为句柄k继续计算下去时可能发出任何片段的请求.

第4.5节 第一级延续

传统上, 加入call/cc这样的控制算子意味着把整个语义改写成延续传递风格. 在我们的框架中却几乎不需要做什么, 因为延续早就在那里了: 一个请求抵达管理者时, 它的句柄k恰好就是程序的其余部分, 也就是当前延续. 我们只需要一个动作, 让句法成分能够拿到它.

我们采用原文的句法: (catchxe)把当前延续绑定到x然后计算e; (throwxe)把e的值交给x所绑定的延续, 并且丢弃当前延续. e ⩴ ( catchxe ) | ( throwxe ) V ⩴ …| K⁡ (κ) κ: V→C A ⩴ …| Con⁡ (f) f: ( V→C ) →C 解释器和管理者的新子句是 ⟦ ( catchxe ) ⟧ ρ = ask⁡ ( Con⁡ ( λκ. v⇐ ⟦e⟧ ρ [ x↦ K⁡ (κ) ] ; κ⁡ (v) ) ) ⟦ ( throwxe ) ⟧ ρ = v⇐ ⟦e⟧ ρ ; case ρ⁡ (x) of | K⁡ (κ) ⇒ ask⁡ ( Con⁡ ( λ_. κ⁡ (v) ) ) |_⇒err admin⁡ ( FX⁡ ( k, Con⁡ (f) ) ,r ) = admin⁡ ( f⁡ (k) ,r ) 控制消息Con⁡(f)携带一个延续的接收者f, 管理者做的唯一一件事就是把当前延续交给它. (catchxe)的接收者把延续以K⁡(κ)的形式放进环境, 计算e, 然后正常返回到κ; (throwxe)的接收者则忽略收到的当前延续, 转而把值交给先前捕获的κ.

跟踪程序 (add1(catchk(sub1(throwk10)))). 为方便起见, 记 f = λκ. v⇐ ⟦ ( sub1 ( throwk10 ) ) ⟧ ρ [ k↦ K⁡ (κ) ] ; κ⁡ (v) inc⁡ (v) = casevof Num⁡ (n) ⇒ Val⁡ ( Num⁡ ( n+1 ) ) |… 解释器给出 ⟦ ( add1 ( catchk… ) ) ⟧ ρ = x⇐ ask⁡ ( Con⁡ (f) ) ; inc⁡ (x) = FX⁡ ( inc, Con⁡ (f) ) . 管理者把句柄inc交给f. 在f的体中, (throwk10)发出请求Con⁡(λ_.inc⁡(Num⁡(10))); 它经过sub1和f的⇐向外传播时, 句柄被扩大了两次, 但这无关紧要, 因为接收者根本不看它: admin⁡ ( FX⁡ ( inc, Con⁡ (f) ) ,r ) = admin⁡ ( f⁡ (inc) ,r ) = admin⁡ ( FX⁡ ( k′ , Con⁡ ( λ_. inc⁡ ( Num⁡ (10) ) ) ) ,r ) = admin⁡ ( inc⁡ ( Num⁡ (10) ) ,r ) = ( Num⁡ (11) ,r ) 其中k′是被扩大了的句柄, 它里面的sub1从未执行.

图4.5.1. [延续片段 (control.rkt)]
(struct K (k))               ; new value: continuation object
(struct Con (receiver))      ; new action: control message

(define/override (interpret exp env)
  (match exp
    [(Catch x body)
     (inAC (Con (lambda (k) (handle (interpret body (extend env x (K k))) k))))]
    [(Throw x e)
     (handle* ([v (interpret e env)])
       (match (lookup env x)
         [(K k) (inAC (Con (lambda (_current-k) (k v))))]
         [_ (inExc "not a continuation")]))]
    [_ (super interpret exp env)]))

(define/override (admin comp resources)
  (match comp
    [(FX k (Con receiver)) (admin (receiver k) resources)]
    [_ (super admin comp resources)]))

这些延续是真正第一级的: 它们可以存进引用单元, 在catch返回之后再被调用, 从而回到过去. 例如下面的程序中catch返回了两次, 第二次返回时n为0:

(run '((lambda (r)
         ((lambda (n)
            (if (zero? n)
                100
                ((lambda (k) (throw k 0)) (deref r))))
          (catch k ((lambda (_) 1) (setref! r k)))))
       (ref 0)))
;; => (answer (Num 100) ...)

注意存储和延续这两个片段从未提到对方, 但它们的组合自然而然地给出了正确的行为.

第5章 组合解释器

现在的问题是: 如何在程序中把这些片段加起来? 原文使用Rice Scheme的第一级模块: 一个语言是导出解释器, 管理者和资源列表的模块, 一个片段是从模块到模块的函数, 称为语言变换器 (language transformer). 今天的Racket里, 与此最贴近而又最容易读的工具是mixin, 即从类到类的函数.

一个语言是一个类, 它有方法interpret, admin, initial-resources (以及用于读入程序的parse). 一个片段的写法总是:

(define foo-mixin
  (mixin (language<%>) ()
    (super-new)
    (define/override (interpret exp env)
      (match exp
        [new-syntax ... (interpret sub-exp env) ...]
        [_ (super interpret exp env)]))
    (define/override (admin comp resources)
      (match comp
        [(FX k new-action) ... (admin (k reply) new-resources) ...]
        [_ (super admin comp resources)]))))

这里有一个微妙之处, 也是原文花了不少笔墨的地方. 一个片段在解释子表达式时, 必须调用完整语言的解释器, 因为子表达式中可能出现尚未添加的片段的句法; 但它把不认识的句法交出去时, 应该交给之前的语言. 原文为此引入了一对名字InterpTop和InterpPrev, 而InterpTop只能在所有片段组合完毕之后才定义, 作为一个全局变量. 用类来实现时, 这对区别是自带的:

  • (interpret ...)是(send this interpret ...), 由动态分派找到完整语言的方法, 即InterpTop;
  • (super interpret ...)调用之前的语言, 即InterpPrev.
这正是面向对象中所谓的开放递归 (open recursion). 于是那两个全局变量就不需要了, 程序中也可以同时存在多个不同的语言:

(define (make-language . mixins)
  (new ((apply compose1 values mixins) base%)))

(define pure-scheme
  (make-language cbv-mixin bool-mixin arith-mixin))
(define core-scheme
  (make-language store-mixin control-mixin cbv-mixin bool-mixin arith-mixin))

原文的组合是 (storeM (controlM (CBVM (arithmM baseM)))), 与此逐字对应. 原文还断言组合的顺序无关紧要, 这是因为每个片段只处理自己的句法和动作, 其余的一律交给super. 我们的测试对五个片段的全部5!=120种排列验证了这一点.

顺带一提, 为了方便测试, 实现中每个片段还提供一个parse方法, 把S-表达式读成自己的抽象语法, 不认识的同样交给super. 这里有一个小陷阱: 变量和应用没有专属的关键字, 若λ演算片段排在算术片段之前, 它就会把(add15)读成一个应用. 解决办法是让每个片段声明自己的关键字, 而λ演算片段在读入变量和应用时避开完整语言的全部关键字. 这又是一次开放递归.

第6章 稳定指称

现在可以精确地说出引言中的目标在什么意义上达到了. 设⟦⋅⟧是某个语言的解释器, ⟦⋅⟧′是它的任意扩展的解释器. 扩展只是给V和A添加了新的形状, 因此旧的值和计算原封不动地也是新的值和计算. 反过来, 把新形状一律映为⊥就得到一个投影π. 原文证明了: ⟦e⟧ ρ = π⁡ ( ⟦e⟧ ′ ρ ) , 其中e是旧语言中的表达式, ρ是只含旧值的环境. 在我们的实现中这一点几乎是显然的: 旧语言的句法由同一段代码解释, 而在只含旧值的环境中这段代码不会遇到新的值, 也就不会发出新的请求. 测试也检验了这一点: 纯函数式的程序在Pure Scheme和Core Scheme中给出相同的值.

如果环境中含有新的值, 例如一个会分配单元的过程, 那么旧的表达式调用它时当然会发出新的请求. 此时等式变为不等式 ι⁡ ( ⟦e⟧ ( π∘ρ ) ) ⊑ ⟦e⟧ ′ ρ , 其中ι是把旧计算看作新计算的嵌入. 它的意思是: 旧语义给出的每个确定的结果, 新语义都给出同样的结果; 新语义只是在旧语义看来发散的地方可能做了更多的事.

第7章 与今天的方法相比

单子与单子变换器. 原文写作时, Moggi的单子已经提出, 而用单子变换器组合解释器 (Liang, Hudak和Jones, POPL 1995) 稍后才出现. 单子变换器的一个众所周知的问题是组合不对称: 异常变换器与状态变换器以不同的顺序叠放, 得到的是不同的语言, 其中一种在抛出异常时撤销副作用, 另一种不撤销. 在扩展直接语义中不存在这个问题, 因为所有的效应都由同一个管理者解释, 片段的组合顺序不影响结果. 代价是语义被固定了: 我们的实现中, 错误之前对存储的修改总是保留在最终的资源中.

代数效应与处理器. 今天的读者大概会觉得这套框架很眼熟. FX⁡(k,a)就是一个代数操作a连同它的续体 (resumption) k; 管理者就是一个效应处理器 (effect handler). Plotkin和Power的代数效应 (2000年代初) 与Plotkin和Pretnar的效应处理器 (2009) 都晚于原文. 最直接继承这篇论文的是Kiselyov, Sabry和Swords的Extensible Effects: An Alternative to Monad Transformers (Haskell 2013), 它明确把本文的思想作为出发点, 并用类型系统记录一个计算可能发出哪些请求. 与这些后来的工作相比, 本文的管理者是唯一的, 位于顶层, 不能嵌套; 一个程序不能在局部为某种请求安装自己的处理器. 延续片段说明了这一限制并不像看起来那么严重: 有了第一级延续, 局部的控制可以由全局的管理者实现.

可扩展的句法. 片段同时扩展句法 (新的变体) 和解释器 (新的子句), 这正是Wadler所说的表达式问题 (expression problem). Swierstra的Data types à la carte (JFP 2008) 在类型化的设定下解决了同样的问题. 我们的实现是动态类型的, 因而只用了最朴素的办法: match失败时交给super.

模块与mixin. 原文使用的Rice Scheme模块系统与后来Racket的单元 (unit) 一脉相承 (Flatt和Felleisen, PLDI 1998); 同年Flatt, Krishnamurthi和Felleisen又给出了mixin的形式化 (POPL 1998). 用单元重写本文的代码会更接近原文, 但mixin更为人所熟知, 而开放递归恰好就是原文需要的东西.

第8章 结语

扩展直接语义的核心只有三个定义: 计算C的两种形状, 顺序组合⇐, 以及管理者admin. 每种效应都被表示为一个请求, 由唯一的管理者在顶层解释; 句法成分之间既不传递存储, 也不传递延续. 其结果是, 一个句法成分的指称不随语言的扩展而改变, 而一个语言的解释器可以由互不知晓的片段组合而成.
