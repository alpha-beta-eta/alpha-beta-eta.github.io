第1章 程序规约

本章引入了一种包含赋值, 条件式, 块和WHILE循环的简单编程语言. 然后用它来描述Hoare用于规约程序部分正确性的记号. Hoare的记号使用形式逻辑记号来表达关于程序变量值的条件. 该记号被非形式化地描述并通过示例加以刻画.

第1.1节 引论

为了从数学上证明一个程序的正确性, 我们必须首先刻画正确本身的含义. 本章我们描述了一种用于刻画命令式程序的预期行为的记号. 这种记号应该归功于C.A.R. Hoare.

执行命令式程序有着改变状态的作用, 直到第7章之前, 我们将状态取为程序变量的值. 为了使用这样的程序, 我们需要建立初始状态, 也就是将一些变量的值设置为有趣的值 (value of interest). 然后我们执行程序. 这将初始状态变换为最终状态. 然后我们检视最终状态里的变量的值来得到预期的结果. 例如, 为了计算y除以x, 我们可能会将x和y分别载入程序变量X和Y. 然后我们可能会执行一个合适的程序 (见第1.4节的例子7) 来将初始状态变换为最终状态以使得变量Q和R分别存放着商和余数.

这些笔记里要使用的编程语言将于下一节进行描述.

第1.2节 一种小语言

程序由诸如赋值和条件式等命令构建而成. 术语程序和命令的确可以算是近义词; 前者只会用于表示完整算法的命令. 这里的术语陈述 (statement)用于程序变量上的条件, 其出现于正确性规约之中 (见第1.3节). 这里存在混淆的风险, 因为一些作者将这个词用于命令 (如for-statement [14]).

现在我们描述我们的小语言里的各种命令的句法 (即形式) 和语义 (即意义). 以下约定将会采用:

  1. 符号V,V1,…,Vn代表任意的变量. 特定变量的例子有X,R,Q等等.
  2. 符号E,E1,…,En代表任意的表达式 (或者说项). 这些是像X+1,2之类的东西, 其指称着值 (通常是数字).
  3. 符号S,S1,…,Sn代表任意的陈述. 这些是像X<Y,X2=1之类的条件, 其要么为真要么为假.
  4. 符号C,C1,…,Cn代表我们编程语言里的任意命令; 这些会在本节的剩余部分进行描述.
项和陈述在第1.5节进行了更为细致的描述.

第1.2.1小节 赋值

句法: V≔E

语义: 状态的改变由将项E之值赋给变量V完成. 所有的变量都假定具有全局作用域.

例子: X:=X+1

这给变量X之值加上一.

第1.2.2小节 序列

句法: C1;…;Cn

语义: 命令C1,…,Cn按照顺序进行执行.

例子: R:=X; X:=Y; Y:=R

变量X和Y之值经由临时变量R进行了互换. 这个命令具有将变量R之值变为变量X之旧值的副作用. {译注: 这个还是这些?}

第1.2.3小节 条件式

句法: IFSTHENC1ELSEC2

语义: 如果陈述S在当前状态下为真, 那么C1被执行. 如果S为假, 那么C2被执行.

例子: IF X<Y THEN MAX:=Y ELSE MAX:=X

变量MAX之值被设为X和Y之值的最大值.

第1.2.4小节 WHILE命令

句法: WHILESDOC

语义: 如果陈述S在当前状态下为真, 那么C被执行, 然后WHILE命令重复. 如果S为假, 那么什么也不做. 因此, C反复执行, 直至S的值变为假. 如果S永远不变为假, 那么该命令的执行永远不终止.

例子: WHILE ¬(X=0) DO X:=X-2

如果X之值非零, 那么其值会减去2, 然后进程重复. 这个WHILE命令将会终止 (此时X有着值0), 如果X的值是一个非负的偶数. 其他状态下都不会终止.

第1.2.5小节 句法总结

我们的小语言的句法可以用BNF记号总结如下:

<command> ::= <variable> := <term>
           |  <command>; ...; <command>
           |  IF <statement> THEN <command> ELSE <command>
           |  WHILE <statement> DO <command>

请注意:

  • 变量, 项, 陈述描述于第1.5节.
  • 这个BNF句法是有歧义的: 例如, IFS1THENC1ELSEC2;C3可能指的是(IFS1THENC1ELSEC2);C3, 也可能指的是IFS1THENC1ELSE(C2;C3). 每当有必要时, 我们会用括号进行澄清.

第1.3节 Hoare记号

在一篇开创性论文 [13] 里C.A.R. Hoare引入了记号{P}C{Q}, 其有时被称为Hoare三元组, 用于刻画一个程序做了什么. 在这样一个Hoare三元组之中:

  • C是一个程序.
  • P和Q是C中用到的程序变量上的条件. 程序变量上的条件以标准的数学记号连带着诸如∧,∨,¬,⇒这样的逻辑联结词书写. 这些在第1.5节有进一步描述.

我们称{P}C{Q}为真, 如果每当C在某个满足P的状态下执行且C的执行终止, 那么C执行终止的状态满足Q.

例子: {X=1}X≔X+1{X=2}. 这里的P是X之值为1这一条件, Q是X之值为2这一条件, C是赋值命令X≔X+1. {X=1}X≔X+1{X=2}为真. {译注: 这个为真是从语义角度而言的.}

一个表达式{P}C{Q}被称为一个部分正确性规约; P被称为其前条件而Q被称为其后条件.

这样的规约之所以是部分的, 是因为即便{P}C{Q}为真, C的执行在满足P的状态下开始也不必终止. 其所要求的仅是如果C终止, 那么Q成立.

一种更强的规约是完全正确性规约. 这种规约没有标准的记号. 我们将使用[P]C[Q].

完全正确性规约[P]C[Q]为真当且仅当以下两个条件满足:

  1. 如果C在满足P状态下开始执行, 那么C终止.
  2. 在终止之后, Q成立.
部分正确性和完全正确性之间的关系可以非正式地表述为以下等式: 完全正确性= 终止性+部分正确性

完全正确性是我们最终感兴趣的, 但通常更容易通过分别建立部分正确性和终止性来证明它.

终止性通常是容易建立的, 但有一些著名的例子并非如此. 例如, 未解决的Collatz猜想与下面的程序是否对X的所有值都终止有关 (见下面的练习):

WHILE X>1 DO
  IF ODD(X) THEN X := (3×X)+1 ELSE X := X DIV 2
(表达式X DIV 2求值为X/2向下取整到一个整数的结果, 不过由于这里条件式的ELSE分支仅在X为偶数时才被执行, 实际上不需要取整.)

著名数学家Paul Erdős关于Collatz猜想说道: 数学对于这样的问题尚未准备好. 他为其解答提供500美元奖励.

第1.4节 一些例子

以下的例子刻画了部分正确性的各种方面.

在以下的例子5, 6, 7中, T是永远为真的条件. 在例子3, 4, 7中, ∧是联结词合取, 即如果P1和P2是条件, 那么P1∧P2是这样的条件, 其为真每当P1和P2均成立.

  1. {X=1}Y≔X{Y=1}
    这是说如果命令Y≔X在一个满足条件X=1的状态下执行, 那么如果执行终止 (在此情况下的确如此), 那么条件Y=1将会成立. 这个规约显然为真.
  2. {X=1}Y≔X{Y=2}
    这是说如果Y≔X的执行始于满足X=1的状态, 那么Y=2将会成立. 这显然为假.
  3. {X=x∧Y=y}R≔X;X≔Y;Y≔R{X=y∧Y=x}
    这是在说如果R≔X;X≔Y;Y≔R的执行终止 (的确如此), 那么X和Y之值就被交换了. 变量x和y没有出现在命令里, 其是用来对于程序变量X和Y的初值进行命名的, 这种变量被称为逻辑变量, 或者辅助变量, 或者幽灵变量.
  4. {X=x∧Y=y}X≔Y;Y≔X{X=y∧Y=x}
    这是在说X≔Y;Y≔X可以交换X和Y之值, 但是实际上这并不为真.
  5. {T}C{Q}
    这是在说每当C终止时, Q成立.
  6. {P}C{T}
    这种规约对于每个条件P和每个命令C为真, 这是因为T总是为真.
  7. {T}
R:=X;
Q:=0;
WHILE Y≤R DO
  (R:=R-Y; Q:=Q+1)
{R < Y ∧ X = R + (Y × Q)}
    这是{T}C{R<Y∧X=R+(Y×Q)}, 其中C是上述的命令. 这个规约为真, 如果每当C的执行终止时, 那么Q是商而R是X除以Y的余数. 这个规约的确为真, 即便X起始为负数!

这个例子里用到了程序变量Q, 读者不应将其与5中所用到的Q混淆. 程序变量Q (注意字体) 遍历数字, 而后条件Q (注意字体) 则遍历陈述. 一般而言, 我们使用typewriter font表示特定的程序变量, 而使用italic font表示遍历陈述的变量. 尽管这种对于字体的微妙运用乍看上去可能令人迷惑, 但是读者一旦理解之后, 两种Q之间的区分就非常显然了. (即便不看字体, 你也应该能够从上下文中区分它们.)

第1.5节 项和陈述

这里用于表达前条件和后条件的记号基于一阶逻辑. 我们只会简要回顾, 因为读者默认已经非常熟悉它了.

以下是原子陈述的例子: T,F, X=1 , R<Y , X= R+ ( Y×Q ) 陈述要么为真要么为假. 陈述T永远为真, 而陈述F永远为假. 陈述X=1为真, 如果X之值等于1. 陈述R<Y为真, 如果R之值小于Y之值. 陈述X=R+(Y×Q)为真, 如果X之值等于R之值与Y和Q之积的和.

陈述由项构建而成, 例如: X,1,R,Y, R+ ( Y×Q ) , Y×Q 项指称着值, 例如数字和字符串, 不像陈述要么为真要么为假. 一些项, 例如1和4+5, 指称着固定的值, 而其他一些项则包含变量, 例如X,Y,Z等等, 其值可能会变化. 我们对于项将会使用常规数学记号, 如以下例子所刻画的那样: X,Y,Z 1,2,325 −X , − ( X+1 ) , ( X×Y ) +Z ( 1+ X2 ) , X! , sin⁡ (X) , rem⁡ ( X,Y )

T和F是分别总是为真和为假的原子陈述. 其他的原子陈述则由项使用谓词构建而成. 以下是更多的一些例子: ODD⁡ (X) , PRIME⁡ (3) , X=1 , ( X+1 ) 2 ≥ X2 ODD和PRIME是谓词的例子, 而=和≥则是中缀谓词的例子. 表达式X,1,3,X+1,(X+1)2,X2是项的例子.

复合陈述由原子陈述使用以下逻辑联结词构建而成: ¬ 否定 ∧ 合取 ∨ 析取 ⇒ 推出 ⇔ 当且仅当 设P和Q是陈述, 那么:

  • ¬P为真如果P为假, 为假如果P为真.
  • P∧Q为真每当P和Q均为真.
  • P∨Q为真如果P或Q为真, 可以同时为真.
  • P⇒Q为真如果每当P为真则Q也为真. 根据约定, 如果P为假, 那么P⇒Q为真. 实际上, 通常将P⇒Q视为等价于¬P∨Q; 然而, 一些称为直觉主义者的哲学家并不赞同这一对于推出的处理方式. {译注: 显然, 不仅是哲学家, 绝大部分编程语言学家也并不赞同.}

第2章 Hoare逻辑

本章讨论了形式化证明的想法. 然后, 我们引入了Hoare逻辑 (或称Floyd-Hoare逻辑) 作为对于程序进行形式化推理的方法.

上一章我们引入了三种可能为真或假的表达式:

  1. 部分正确性规约{P}C{Q}.
  2. 完全正确性规约[P]C[Q].
  3. 数学陈述, 例如(X+1)2=X2+2×X+1.

这个证明由一系列行构成, 每行都是某个公理的实例或者根据之前的行由推理规则推出. 这个证明的最后一行是其所证明的陈述, 也就是(X+1)2=X2+2×X+1.

为了构造部分正确性规约的形式化证明, 需要公理和推理规则. 这正是Hoare逻辑所提供的. 该演绎系统的形式化表述归功于Hoare [13], 但其中一些基本思想源自Floyd [9].

Hoare逻辑中的证明是一系列行的序列, 其中每一行要么是该逻辑的一条公理, 要么是由前面的行通过该逻辑的一条推理规则推导而来.

构造形式化证明的原因在于试图确保只使用可靠的演绎方法. 有了可靠的公理和推理规则, 我们就可以确信所得出的结论是真的. 另一方面, 如果任何公理或推理规则是不可靠的, 那么就有可能推导出错误的结论; 例如: 1. −1 × −1 = −1 × −1 =的自反性. 2. −1 × −1 = ( −1 ) × ( −1 ) 之于×的分配律. 3. −1 × −1 = ( −1 ) 2 ( ) 2 的定义. 4. −1 × −1 = −1 的定义. 5. 1 = −1 鉴于 −1 × −1 =1 . 6. 1 = −1 鉴于 1 =1 .

形式化证明明确指出了为得出结论所使用的公理和推理规则. 人们很容易提出一些看似合理但实际上不可靠的程序推理规则. 计算机程序的正确性证明往往非常复杂, 需要形式化方法来确保其有效性. 因此, 将所使用的推理原则完全显式化是很重要的, 这样才能对其可靠性进行分析.

对于某些应用而言, 正确性尤为重要. 例子包括生命攸关的系统, 如核反应堆控制器, 汽车制动系统, 电传飞控飞机以及软件控制的医疗设备. 曾有一起法律诉讼源于一台癌症治疗设备因软件缺陷导致辐射过量, 造成数人死亡 [15]. 当穷举测试不可能实现时 (几乎总是如此), 形式化正确性证明提供了一种确认程序中不存在缺陷的方法.

本章将解释并举例说明用于程序推理的Hoare演绎系统. 该系统的可靠性和完备性的数学分析将在第4章中讨论.

第2.1节 Hoare逻辑的公理和规则

正如本章开头所讨论的, 一个命题的形式化证明是以该命题为最后一行的一个行序列, 其中每一行要么是一条公理的实例, 要么是由前面的行通过一条推理规则推导而来. 若S是一个命题 (无论是普通数学的还是Hoare逻辑的), 我们记⊢S来表示S有一个证明. 拥有证明的命题称为定理. 如前所述, 在本讲义中只描述Hoare逻辑的公理和推理规则; 因此, 若S是一个数学定理, 我们将直接断言⊢S而不给出任何形式化的论证. 当然, 为了达到完全的严格性, 这些断言必须被证明, 但如何做到这一点的细节假定读者已经了解 (例如通过逻辑与证明课程).

Hoare逻辑的公理在下面通过模式来指定, 这些模式可以被实例化以得到特定的部分正确性规约. Hoare逻辑的推理规则将用如下形式的记号来描述: ⊢ S1 ⋯ ⊢ Sn ⊢S 这是说结论⊢S可以从⊢S1,…,⊢Sn推导而来, 后者是该规则的假设. 这些假设可以全部是Hoare逻辑的定理 (如下面的顺序规则), 也可以是Hoare逻辑定理与数学定理的混合 (如第2.1.2小节中描述的前条件加强规则).

第2.1.1小节 赋值公理

赋值公理表达了这样一个事实: 在执行赋值命令V≔E之后, 变量V的值等于执行前表达式E的值. 为了将此形式化, 注意到如果一个命题P在赋值之后为真, 那么在执行赋值之前, 将P中的V替换为E所得到的命题必须为真. {译注: 这似乎和以下公理所表达的内容方向相反.}

为了形式化地表达这一点, 定义P[E/V]以表示将P中所有V的出现替换为E之结果. P[E/V]读作P with E for V. 例如, ( X+1 >X ) [ Y+Z /X ] = ( ( Y+Z ) +1 > Y+Z ) 记住这个记号的方法是消去律 V [ E/V ] =E 这类比于分式的消去性质 v× ( e/v ) =e

Hoare赋值公理
⊢ { P [ E/V ] } V≔E {P} 其中V是任意的变量, E是任意的表达式, P是任意的陈述, 而P[E/V]代表将陈述P中变量V的所有出现都替换为项E.

赋值公理的实例有:

  1. ⊢{Y=2}X≔2{Y=X}
  2. ⊢{X+1=n+1}X≔X+1{X=n+1}
  3. ⊢{E=E}X≔E{X=E}, 如果X在E中没有出现.

许多人会感到赋值公理和他们所期望的相反. 两种常见的错误直觉如下:

  1. ⊢{P}V≔E{P[V/E]}
    (未完待续)
  2. ⊢{P}V≔E{P[E/V]}
    如果取P为X=0, V为X, E为1, 就会得到⊢{X=0}X≔1{1=0}, 这显然是错误的. {译注: 也就是unsound.}

关于赋值公理容易产生错误直觉这一事实表明, 拥有严格的手段来确立公理和规则的有效性是很重要的. 我们将在后面的第4章中深入讨论这个主题, 届时我们将给出我们这个小型编程语言的形式化语义, 然后证明Hoare逻辑的公理和推理规则是可靠的. 当然, 这一过程只有在我们相信形式化语义本身的正确性的前提下, 才能增强我们对公理和规则的信心. 上述简单的赋值公理对于真实的编程语言是不成立的. 例如, G. Ligler [17] 的工作表明, 它在(现已过时的)语言Algol 60中以六种不同的方式失效.

第2.1.2小节 前条件强化

下一条Hoare逻辑规则允许第18页的i和ii的前条件得到简化. 回忆一下, ⊢ S1 ⋯ ⊢ Sn ⊢S 表示⊢S可由⊢S1,…,⊢Sn推导出来. {译注: 这是句法概念.}

使用该记号, 前条件强化规则为

前条件强化
⊢ P⇒ P′ ⊢ { P′ } C {Q} ⊢ {P} C {Q}

例子

  1. 根据算术事实⊢X=n⇒X+1=n+1, 以及第18页的2, 藉由前条件强化可以得到 ⊢ { X=n } X≔ X+1 { X= n+1 } 这里的变量n是辅助变量或者说幽灵变量的例子. 正如之前所描述的 (见第10页), 辅助变量是出现于部分正确性规约{P}C{Q}中但未出现在命令C中的变量. 这样的变量用于将C执行前后的状态中的值关联起来. 例如, 以上的规约里说的是如果X之值为n, 那么在执行赋值X≔X+1之后其值将会变成n+1.
  2. 根据逻辑事实⊢T⇒E=E, 以及第18页的3, 我们可以推导出如果X没有出现在E之中, 那么: ⊢ {T} X≔E { X=E }

第2.1.3小节 后条件弱化

正如之前的规则允许部分正确性规约里的前条件被强化, 以下的规则允许我们对于后条件进行弱化.

后条件弱化
⊢ {P} C { Q′ } ⊢ Q′ ⇒Q ⊢ {P} C {Q}

例子: 以下是一个小小的形式证明. 1. ⊢ { R=X ∧ 0=0 } Q≔0 { R=X ∧ Q=0 } 根据赋值公理. 2. ⊢ R=X ⇒ R=X ∧ 0=0 根据纯粹逻辑. 3. ⊢ { R=X } Q≔0 { R=X ∧ Q=0 } 根据前条件强化. 4. ⊢ R=X ∧ Q=0 ⇒ R= X+ ( Y×Q ) 根据算术律. 5. ⊢ { R=X } Q≔0 { R= X+ ( Y×Q ) } 根据后条件弱化.

前条件强化和后条件弱化规则有时被称为rules of consequence.

第2.1.4小节 规约合取与析取

以下两条规则提供了将关于相同命令的不同规约组合起来的方法.

规约合取
⊢ { P1 } C { Q1 } ⊢ { P2 } C { Q2 } ⊢ { P1 ∧ P2 } C { Q1 ∧ Q2 }
规约析取
⊢ { P1 } C { Q1 } ⊢ { P2 } C { Q2 } ⊢ { P1 ∨ P2 } C { Q1 ∨ Q2 }

这些规则对于将证明拆成独立的任务而言是有用的. 例如, 其允许通过单独证明⊢{P}C{Q1}和⊢{P}C{Q2}而证明⊢{P}C{Q1∧Q2}.

剩余的这些规则允许复合命令的性质由其分量的性质推导而来.

第2.1.5小节 顺序规则

接下来的规则允许我们由C1和C2的规约推导出序列C1;C2的部分正确性规约.

顺序规则
⊢ {P} C1 {Q} ⊢ {Q} C2 {R} ⊢ {P} C1 ; C2 {R}

第2.1.8小节 WHILE规则

如果⊢{P∧S}C{P}, 那么我们称: 每当S成立, P是C的一个不变量. WHILE规则是说, 如果P每当测试条件成立时是WHILE命令之体的一个不变量, 那么P是整个WHILE命令的一个不变量. 换言之, 如果执行C一次能够保持P的为真, 那么执行C任意多次也能够保持P的为真.

WHILE命令也表达了这样的事实, 在一个WHILE命令终止之后, 测试条件必然为假 (否则的话, 之前就不会终止).

WHILE规则
⊢ { P∧S } C {P} ⊢ {P} WHILESDOC { P∧ ¬S }

例子: 根据之前的规则可得: ⊢ { X= R+ ( Y×Q ) } R≔ R−Y ; Q≔ Q+1 { X= R+ ( Y×Q ) } 因此, 根据前条件强化, 可知 ⊢ { X= R+ ( Y×Q ) ∧ Y≤R } R≔ R−Y ; Q≔ Q+1 { X= R+ ( Y×Q ) } 于是, 根据WHILE规则, 取P为X=R+(Y×Q), 可以得到 ⊢ { X= R+ ( Y×Q ) } WHILE Y≤R DO ( R≔ R−Y ; Q≔ Q+1 ) { X= R+ ( Y×Q ) ∧ ¬ ( Y≤R ) } 应用赋值公理两次 (以及顺序公理), 容易推导出 ⊢ {T} R≔X ; Q≔0 { X= R+ ( Y×Q ) } 根据以上两个结果, 以及顺序规则和后条件弱化, 可以推得 ⊢ {T} R≔X ; Q≔0 ; WHILE Y≤R DO ( R≔ R−Y ; Q≔ Q+1 ) { R<Y ∧ X= R+ ( Y×Q ) }

除了WHILE规则这个例外, 目前所有描述的公理和规则对于完全正确性和部分正确性都是可靠的. 这是因为我们的小语言中唯一可能不终止的命令就是WHILE命令. {译注: 并且, 根据精心(且脆弱)的安排, 如果该语言里的运算和谓词都是完全的, 那么该语言甚至不会抛出异常.} 现在考虑如下证明:

  1. ⊢{T}X≔0{T} (赋值公理)
  2. ⊢{T∧T}X≔0{T} (前条件强化)
  3. ⊢{T}WHILETDOX≔0{T∧¬T} (2和WHILE规则)
若是WHILE规则对于完全正确性也是适用的, 那么上述证明就会表明: ⊢ [T] WHILETDO X≔0 [ T∧ ¬T ] 但这显然不对, 因为WHILETDOX≔0并不终止, 但即便它终止了, T∧¬T也不可能在任何结果状态下成立.

第3章 机械化程序验证

本章描述了一个简单的程序验证器的架构. 其操作相对于Hoare逻辑的规则而澄清.

在摆弄了一些例子之后, 以下两件事情一目了然:

  1. 证明一般冗长且乏味 (即便要验证的程序相当简单).
  2. 存在大量琐碎的细节需要弄对, 其中许多极其平凡, 例如证明⊢(R=X∧Q=0)⇒(X=R+Y×Q).

人们已经进行了许多尝试(并且仍在继续), 试图通过设计系统来自动完成正确性证明, 让这些系统处理在Hoare逻辑中生成形式化证明时那些枯燥而繁琐的部分. 不幸的是, 逻辑学家已经证明, 从原理上讲, 不可能设计出一种判定过程来自动判定任意数学命题的真假 [10]. 然而, 这并不意味着我们无法拥有能够证明许多有用定理的过程. 一般判定过程的不存在仅仅表明, 我们不能期望自动证明一切. 在实践中, 构建一个能够将验证过程中许多枯燥和常规方面机械化的系统是完全可行的. 本章描述了一种常用的实现方法.

尽管不可能自动判定任意命题的真假, 但检验一个任意的形式化证明是否有效却是可能的. 这包括检查证明中每一行出现的结果是否确实是公理, 或者是由前面的行推导出的结论. 由于程序正确性的证明通常非常冗长且枯燥, 手动生成时往往会包含错误. 因此, 即使证明只能在人工辅助下生成, 对其进行机械化检验仍然是有价值的.

第3.1节 概览

前一章展示了如何证明{P}C{Q}, 方法是证明C的各部分之性质, 然后(以合适的证明规则)将它们拼在一起以获得关于C本身的预期性质. 例如, 为了证明⊢{P}C1;C2{Q}, 我们首先证明⊢{P}C1{R}和⊢{R}C2{Q} (对于某个合适的R而言), 然后根据顺序规则可以推出⊢{P}C1;C2{Q}.

这种过程被称为前向证明, 因为人们由公理通过规则向前推进到结论. 在实践中, 更为自然的是后向工作: 从表明{P}C{Q}的目标开始, 我们生成子目标, 子目标, 如此反复直至问题解决. 例如, 假定我们想要证明: ⊢ { X=x ∧ Y=y } R≔X ; X≔Y ; Y≔R { Y=x ∧ X=y } 那么根据赋值公理和顺序规则, 证明以下子目标就足够了: ⊢ { X=x ∧ Y=y } R≔X ; X≔Y { R=x ∧ X=y } 鉴于⊢{R=x∧X=y}Y≔R{Y=x∧X=y}. 根据类似的论证, 这个子目标可以被归约为 ⊢ { X=x ∧ Y=y } R≔X { R=x ∧ Y=y } 这显然可由赋值公理推出.

这一章描述了如何形式化这样一种面向目标的证明方法.

这里所描述的验证系统可以被视为一个证明检查器, 同时它也为证明的生成提供了一定的帮助. 下图给出了该系统的概览.

要证明的规约 →人类专家 注解了的规约 →vc生成器 逻辑陈述集合 →定理证明器 简化的验证条件集合 →人类专家 证明结束

该系统的输入是一个部分正确性规约, 其中标注了描述变量之间关系的数学陈述. 系统从标注后的规约中生成一组纯数学陈述, 称为验证条件 (即VC). 在3.5节中将会证明, 如果这些验证条件是可证明的, 那么原始规约就可以从Hoare逻辑的公理和规则中推导出来.

验证条件被传递给一个定理证明器程序, 该程序尝试自动地证明它们; 如果证明失败, 则向用户寻求建议. 我们将集中讨论与Hoare逻辑相关的方面, 而对定理证明本身着墨甚少.

当前大量研究的目标是构建能够将缓慢且昂贵的人类专家的参与降到最低的系统. 这可以通过以下途径实现:

  • 减少所需标注的数量和复杂度, 以及
  • 增强定理证明器的能力.

下一节将解释验证条件的工作原理. 在3.5节中, 将依据Hoare逻辑的公理和规则来论证其使用的合理性. 除了作为机械化验证系统的基础之外, 验证条件也是手工进行证明的一种有用方式.

第3.2节 验证条件

以下各节描述了如何将面向目标的证明风格形式化. 为了证明一个目标{P}C{Q}, 需要完成三件事. 这些将在后文中详细解释, 但这里先给出一个简要概述:

  1. 通过在程序C中插入陈述 (通常称为断言) 来对其进行标注, 这些断言表达了在各个中间点上应当成立的条件. 这一步骤是棘手的, 需要智慧以及对程序工作方式的深刻理解. 将其自动化是一个人工智能问题.
  2. 然后从标注后的规约中生成一组称为验证条件 (简称VC) 的逻辑陈述. 这一过程是纯机械的, 很容易由程序完成.
  3. 证明这些验证条件. 将其自动化同样是一个人工智能问题.

我们将证明, 如果能够证明由{P}C{Q}生成的所有验证条件 (其中C已被适当注解), 则⊢{P}C{Q}.

由于验证条件只是数学陈述, 可以将上述第2步视为将验证问题编译或翻译为传统数学问题的过程.

赋值命令

条件式
由 {P} IFSTHEN C1 ELSE C2 {Q} 生成的验证条件为

  2. { P∧ ¬S } C2 {Q} 所生成的验证条件

  2. C1;…;Cn−1;V≔E.
在这两种情形下, C1;…;Cn−1都是正确注解了的命令.

序列
  1. {P} C1 ;…; C n−1 ; {R} Cn {Q} (其中Cn不是一个赋值) 所生成的验证条件为:

第3.5节 验证条件的澄清

本节将证明, 若一个带注解的规约{P}C{Q}所生成的验证条件是可证的, 则该规约在Hoare逻辑中也是可证的, 即⊢{P}C{Q}. 这说明验证条件是充分的, 但并不意味着它们是必要的. 事实上, 验证条件是最弱的充分条件, 但我们在此既不对此作更精确的表述, 也不深入讨论细节. 关于前条件的深入研究可参见Dijkstra的著作 [8].

容易证明验证条件不是必要的, 即{P}C{Q}的验证条件不可证并不意味着⊢{P}C{Q}不可推导. 例如, 带注解规约{T}WHILEFDO{F}X≔0{T}的验证条件是不可证的, 但该Hoare三元组在Hoare逻辑中是可证的. {译注: 当我们说其在Hoare逻辑中是可证时, 是直接将命令中的注解完全抛弃了的.}

验证条件充分性的论证将对C的结构进行归纳. 这类归纳论证包含两个部分. 首先, 证明结论对赋值命令成立. 其次, 证明当C不是赋值命令时, 若结论对C的各组成命令成立 (这称为归纳假设), 则结论对C也成立. 前者称为归纳基础, 后者称为归纳步骤. 由归纳基础和归纳步骤即可得出结论对所有命令成立.

第3.5.1小节 赋值

{P}V≔E{Q}唯一的验证条件是P⇒Q[E/V]. 如果这是可证的, 那么鉴于⊢{Q[E/V]}V≔E{Q} (赋值公理), 根据前条件强化可以推出⊢{P}V≔E{Q}.

第3.5.2小节 条件式

如果{P}IFSTHENC1ELSEC2{Q}的验证条件是可证的, 那么{P∧S}C1{Q}和{P∧¬S}C2{Q}的验证条件都是可证的. 根据归纳假设, 我们可以假定⊢{P∧S}C1{Q}和⊢{P∧¬S}C2{Q}. 因此, 根据条件式规则可得⊢{P}IFSTHENC1ELSEC2{Q}.

第3.5.3小节 序列

存在两种需要考虑的情形:

  1. 如果{P}C1;…;Cn−1;{R}Cn{Q}的验证条件是可证明的, 那么{P}C1;…;Cn−1{R}和{R}Cn{Q}的验证条件都必须是可证明的, 因而根据规则有⊢{P}C1;…;Cn−1{R}和⊢{R}Cn{Q}. 于是, 根据顺序规则, 我们可得⊢{P}C1;…;Cn−1;Cn{Q}.
  2. 如果{P}C1;…;Cn−1;V≔E{Q}的验证条件是可证明的, 那必然是{P}C1;…;Cn−1{Q[E/V]}的验证条件也是可证的这一情形, 因而根据归纳, 我们有⊢{P}C1;…;Cn−1{Q[E/V]}. 然后, 根据赋值公理可以得到⊢{Q[E/V]}V≔E{Q}, 于是由顺序规则得到⊢{P}C1;…;Cn−1;V≔E{Q}.

第3.5.4小节 WHILE命令

如果{P}WHILESDO{R}C{Q}生成的验证条件是可证的, 那么⊢P⇒R, ⊢(R∧¬S)⇒Q且由{R∧S}C{R}所生成的验证条件是可证的. 根据归纳可得⊢{R∧S}C{R}, 因而根据WHILE规则有⊢{R}WHILESDOC{R∧¬S}. 然后, 根据consequence规则可得⊢{P}WHILESDOC{Q}.

第4章 可靠性和完备性

乍看上去似乎采用ii是最为自然的选择. 然而, 这会使得理解算术定律是否应该成立变得棘手. 例如, (1/0)×0应该等于0还是某种错误值? 如果是后者, 那么就会导致n×0=0不再是有效的算术定律了. {译注: 含义是不能用其进行项重写化简.} 使用未定义或者 (and/or) 错误值或许也能让一切运转起来, 只不过其带来的理论有点混乱. 我们将会在这里假定算术表达式总是指称着数字, 只不过在某些情形下这个数字确切是什么未加刻画. 例如, 我们将会假定对于任意的m和n, m/n总会指称着某个数字, 但是其唯一假定的性质为 ¬ ( n=0 ) ⇒ ( m/n ) ×n =m 由此关于m/0并不能推出任何东西.

另一种处理错误的方法在于扩展命令的语义, 允许错误和状态一样作为结果. 这种方法用在第7章以处理内存错误, 但是类似的想法也能用来处理表达式求值错误 (尽管代价是语义更为复杂).

第6章 程序精化

Floyd-Hoare逻辑是一种证明现有程序满足其规约的方法. 它也可以作为将规约精化为程序的基础——即作为一种程序设计方法论的基础.

第6.1节 引论

程序员的任务可以被看作: 给定一个由前条件P和后条件Q组成的规约, 然后构造出一个命令C, 使得[P]C[Q]成立.

精化理论提出了从规约P和Q计算出程序C的规则. 一个关键思想来自芬兰的Ralph Back (后来被Joseph Morris和Carroll Morgan各自独立地重新发现), 即引入一类新的程序构造, 称为规约. 这些构造在句法上扮演与命令相同的角色, 但它们不可直接执行, 不过它们能保证在给定的前条件下达成给定的后条件. 由此产生的广义编程语言包含纯规约, 纯代码以及二者的混合体. 这样的语言被称为宽谱语言.

本章采用的方法遵循Morgan所发展的精化风格, 但其基础是Floyd-Hoare逻辑, 而非Dijkstra的最弱前条件理论 (见4.3.3节). 与传统方法相比, 这一基础更加具体和句法化: 规约被等同于其所有可能实现的集合, 精化则被表示为对普通命令集合的操作. 这种方法旨在利用前面各章所引入的记号和概念工具, 传达 (Morgan风格的) 精化的外观和感觉.

记号[P,Q]将用于表示规约, 因此: [ P,Q ] = { C| ⊢ [P] C [Q] } 精化过程将由一系列步骤组成, 这些步骤通过系统性的设计决策逐步缩小可能实现的集合, 直到达到唯一的实现. 因此, 从规约S到实现C的精化具有如下形式: S⊇ S1 ⊇ S2 ⊇⋯⊇ Sn ⊇ {C}

初始规约S具有[P,Q]的形式, 每个中间规约Si都是通过对其前驱Si−1应用一条精化律而得到的.

在文献中, S⊇S′通常写作S⊑S′. 这里使用⊇而非更抽象的⊑, 反映了精化作为逐步缩小实现集合这一具体解释.
