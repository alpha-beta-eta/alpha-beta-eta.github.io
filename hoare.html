第1章 程序规约

第1.1节 引论

为了从数学上证明一个程序的正确性, 我们必须首先刻画正确本身的含义. 本章我们描述了一种用于刻画命令式程序的预期行为的记号. 这种记号应该归功于C.A.R. Hoare.

执行命令式程序有着改变状态的作用, 直到第7章之前, 我们将状态取为程序变量的值. 为了使用这样的程序, 我们需要建立初始状态, 也就是将一些变量的值设置为有趣的值 (value of interest). 然后我们执行程序. 这将初始状态变换为最终状态. 然后我们检视最终状态里的变量的值来得到预期的结果. 例如, 为了计算y除以x, 我们可能会将x和y分别载入程序变量X和Y. 然后我们可能会执行一个合适的程序 (见第1.4节的例子7) 来将初始状态变换为最终状态以使得变量Q和R分别存放着商和余数.

这些笔记里要使用的编程语言将于下一节进行描述.

第1.2节 一种小语言

程序由诸如赋值和条件式等命令构建而成. 术语程序和命令的确可以算是近义词; 前者只会用于表示完整算法的命令. 这里的术语陈述 (statement)用于程序变量上的条件, 其出现于正确性规约之中 (见第1.3节). 这里存在混淆的风险, 因为一些作者将这个词用于命令 (如for-statement [14]).

现在我们描述我们的小语言里的各种命令的句法 (即形式) 和语义 (即意义). 以下约定将会采用:

  1. 符号V,V1,…,Vn代表任意的变量. 特定变量的例子有X,R,Q等等.
  2. 符号E,E1,…,En代表任意的表达式 (或者说项). 这些是像X+1,2之类的东西, 其指称着值 (通常是数字).
  3. 符号S,S1,…,Sn代表任意的陈述. 这些是像X<Y,X2=1之类的条件, 其要么为真要么为假.
  4. 符号C,C1,…,Cn代表我们编程语言里的任意命令; 这些会在本节的剩余部分进行描述.
项和陈述在第1.5节进行了更为细致的描述.

第1.2.1小节 赋值

句法: V≔E

语义: 状态的改变由将项E之值赋给变量V完成. 所有的变量都假定具有全局作用域.

例子: X:=X+1

这给变量X之值加上一.

第1.2.2小节 序列

句法: C1;⋯;Cn

语义: 命令C1,…,Cn按照顺序进行执行.

例子: R:=X; X:=Y; Y:=R

变量X和Y之值经由临时变量R进行了互换. 这个命令具有将变量R之值变为变量X之旧值的副作用. {译注: 这个还是这些?}

第1.2.3小节 条件式

句法: IFSTHENC1ELSEC2

语义: 如果陈述S在当前状态下为真, 那么C1被执行. 如果S为假, 那么C2被执行.

例子: IF X<Y THEN MAX:=Y ELSE MAX:=X

第1.2.4小节 WHILE命令

句法: WHILESDOC

语义: 如果陈述S在当前状态下为真, 那么C被执行, 然后WHILE命令重复. 如果S为假, 那么什么也不做. 因此, C反复执行, 直至S的值变为假. 如果S永远不变为假, 那么该命令的执行永远不终止.

例子: WHILE ¬(X=0) DO X:=X-2

如果X之值非零, 那么其值会减去2, 然后进程重复. 这个WHILE命令将会终止 (此时X有着值0), 如果X的值是一个非负的偶数. 其他状态下都不会终止.

第1.3节 Hoare记号

在一篇开创性论文 [13] 里C.A.R. Hoare引入了记号{P}C{Q}, 其有时被称为Hoare三元组, 用于刻画一个程序做了什么. 在这样一个Hoare三元组之中:

  • C是一个程序.
  • P和Q是C中用到的程序变量上的条件. 程序变量上的条件以标准的数学记号连带着诸如∧,∨,¬,⇒这样的逻辑联结词书写. 这些在第1.5节有进一步描述.

我们称{P}C{Q}为真, 如果每当C在某个满足P的状态下执行且C的执行终止, 那么C执行终止的状态满足Q.

例子: {X=1}X:=X+1{X=2}. 这里的P是

一个表达式{P}C{Q}被称为一个部分正确性规约; P被称为其前条件而Q被称为其后条件.

第2章 Hoare逻辑

本章讨论了形式化证明的想法. 然后, 我们引入了Hoare逻辑 (或称Floyd-Hoare逻辑) 作为对于程序进行形式化推理的方法.

上一章我们引入了三种可能为真或假的表达式:

  1. 部分正确性规约{P}C{Q}.
  2. 完全正确性规约[P]C[Q].
  3. 数学陈述, 例如(X+1)2=X2+2×X+1.
我们假定读者已经知道如何证明简单的数学陈述, 例如以上的iii中的那条. 例如, 以下是该事实的一个证明. 1. ( X+1 ) 2 = ( X+1 ) × ( X+1 ) ( ) 2 的定义. 2. ( X+1 ) × ( X+1 ) = ( X+1 ) ×X + ( X+1 ) ×1 ×之于+的左分配律. 3. ( X+1 ) 2 = ( X+1 ) ×X + ( X+1 ) ×1 将第2行代入第1行. 4. ( X+1 ) ×1 = X+1 1的恒元律. 5. ( X+1 ) ×X = X×X + 1×X ×之于+的右分配律. 6. ( X+1 ) 2 = X×X + 1×X +X+1 将第4行和第5行代入第3行. 7. 1×X = X 1的恒元律. 8. ( X+1 ) 2 = X×X +X+X+1 将第7行代入第6行. 9. X×X = X2 ( ) 2 的定义. 10. X+X = 2×X 2= 1+1 ,分配律 11. ( X+1 ) 2 = X2 + 2×X +1 将第9行和第10行代入第8行.

这个证明由一系列行构成, 每行都是某个公理的实例或者根据之前的行由推理规则推出. 这个证明的最后一行是其所证明的陈述, 也就是(X+1)2=X2+2×X+1.

为了构造部分正确性规约的形式化证明, 需要公理和推理规则. 这正是Hoare逻辑所提供的. 该演绎系统的形式化表述归功于Hoare [13], 但其中一些基本思想源自Floyd [9].

Hoare逻辑中的证明是一系列行的序列, 其中每一行要么是该逻辑的一条公理, 要么是由前面的行通过该逻辑的一条推理规则推导而来.

构造形式化证明的原因在于试图确保只使用可靠的演绎方法. 有了可靠的公理和推理规则, 我们就可以确信所得出的结论是真的. 另一方面, 如果任何公理或推理规则是不可靠的, 那么就有可能推导出错误的结论; 例如:

形式化证明明确指出了为得出结论所使用的公理和推理规则. 人们很容易提出一些看似合理但实际上不可靠的程序推理规则. 计算机程序的正确性证明往往非常复杂, 需要形式化方法来确保其有效性. 因此, 将所使用的推理原则完全显式化是很重要的, 这样才能对其可靠性进行分析.

对于某些应用而言, 正确性尤为重要. 例子包括生命攸关的系统, 如核反应堆控制器, 汽车制动系统, 电传飞控飞机以及软件控制的医疗设备. 曾有一起法律诉讼源于一台癌症治疗设备因软件缺陷导致辐射过量, 造成数人死亡 [15]. 当穷举测试不可能实现时 (几乎总是如此), 形式化正确性证明提供了一种确认程序中不存在缺陷的方法.

本章将解释并举例说明用于程序推理的Hoare演绎系统. 该系统的可靠性和完备性的数学分析将在第4章中讨论.

第2.1节 Hoare逻辑的公理和规则

正如本章开头所讨论的, 一个命题的形式化证明是以该命题为最后一行的一个行序列, 其中每一行要么是一条公理的实例, 要么是由前面的行通过一条推理规则推导而来. 若S是一个命题 (无论是普通数学的还是Hoare逻辑的), 我们记⊢S来表示S有一个证明. 拥有证明的命题称为定理. 如前所述, 在本讲义中只描述Hoare逻辑的公理和推理规则; 因此, 若S是一个数学定理, 我们将直接断言⊢S而不给出任何形式化的论证. 当然, 为了达到完全的严格性, 这些断言必须被证明, 但如何做到这一点的细节假定读者已经了解 (例如通过逻辑与证明课程).

Hoare逻辑的公理在下面通过模式来指定, 这些模式可以被实例化以得到特定的部分正确性规约. Hoare逻辑的推理规则将用如下形式的记号来描述: ⊢ S1 ⋯ ⊢ Sn ⊢S 这是说结论⊢S可以从⊢S1,…,⊢Sn推导而来, 后者是该规则的假设. 这些假设可以全部是Hoare逻辑的定理 (如下面的顺序规则), 也可以是Hoare逻辑定理与数学定理的混合 (如第2.1.2节中描述的前条件加强规则).

第2.1.1小节 赋值公理

赋值公理表达了这样一个事实: 在执行赋值命令V≔E之后, 变量V的值等于执行前表达式E的值. 为了将此形式化, 注意到如果一个命题P在赋值之后为真, 那么在执行赋值之前, 将P中的V替换为E所得到的命题必须为真. {译注: 这似乎和以下公理所表达的内容方向相反.}

为了形式化地表达这一点, 定义P[E/V]以表示将P中所有V的出现替换为E之结果. P[E/V]读作Pwith E for V. 例如, ( X+1 >X ) [ Y+Z /X ] = ( ( Y+Z ) +1 > Y+Z ) 记住这个记号的方法是消去律 V [ E/V ] =E 这类比于分式的消去性质 v× ( e/v ) =e

Hoare赋值公理
⊢ { P [ E/V ] } V≔E {P} 其中V是任意的变量, E是任意的表达式, P是任意的陈述, 而P[E/V]代表将陈述P中变量V的所有出现都替换为项E.

赋值公理的实例有:

  1. ⊢{Y=2}X≔2{Y=X}
  2. ⊢{X+1=n+1}X≔X+1{X=n+1}
  3. ⊢{E=E}X≔E{X=E}, 如果X在E中没有出现.

许多人会感到赋值公理和他们所期望的相反. 两种常见的错误直觉如下:

  1. ⊢{P}V≔E{P[V/E]}
  2. ⊢{P}V≔E{P[E/V]}

关于赋值公理容易产生错误直觉这一事实表明, 拥有严格的手段来确立公理和规则的有效性是很重要的. 我们将在后面的第4章中深入讨论这个主题, 届时我们将给出我们这个小型编程语言的形式化语义, 然后证明Hoare逻辑的公理和推理规则是可靠的. 当然, 这一过程只有在我们相信形式化语义本身的正确性的前提下, 才能增强我们对公理和规则的信心. 上述简单的赋值公理对于真实的编程语言是不成立的. 例如, G. Ligler [17] 的工作表明, 它在(现已过时的)语言Algol 60中以六种不同的方式失效.

第3章 机械化程序验证

本章描述了一个简单的程序验证器的架构. 其操作相对于Hoare逻辑的规则而澄清.

在摆弄了一些例子之后, 以下两件事情一目了然:

  1. 证明一般冗长且乏味 (即便要验证的程序相当简单).
  2. 存在大量琐碎的细节需要弄对, 其中许多极其平凡, 例如证明⊢(R=X∧Q=0)⇒(X=R+Y×Q).

人们已经进行了许多尝试(并且仍在继续), 试图通过设计系统来自动完成正确性证明, 让这些系统处理在Hoare逻辑中生成形式化证明时那些枯燥而繁琐的部分. 不幸的是, 逻辑学家已经证明, 从原理上讲, 不可能设计出一种判定过程来自动判定任意数学命题的真假 [10]. 然而, 这并不意味着我们无法拥有能够证明许多有用定理的过程. 一般判定过程的不存在仅仅表明, 我们不能期望自动证明一切. 在实践中, 构建一个能够将验证过程中许多枯燥和常规方面机械化的系统是完全可行的. 本章描述了一种常用的实现方法.

尽管不可能自动判定任意命题的真假, 但检验一个任意的形式化证明是否有效却是可能的. 这包括检查证明中每一行出现的结果是否确实是公理, 或者是由前面的行推导出的结论. 由于程序正确性的证明通常非常冗长且枯燥, 手动生成时往往会包含错误. 因此, 即使证明只能在人工辅助下生成, 对其进行机械化检验仍然是有价值的.

第3.1节 概览

前一章展示了如何证明{P}C{Q}, 方法是证明C的各部分之性质, 然后(以合适的证明规则)将它们拼在一起以获得关于C本身的预期性质. 例如, 为了证明⊢{P}C1;C2{Q}, 我们首先证明⊢{P}C1{R}和⊢{R}C2{Q} (对于某个合适的R而言), 然后根据顺序规则可以推出⊢{P}C1;C2{Q}.

这种过程被称为前向证明, 因为人们由公理通过规则向前推进到结论. 在实践中, 更为自然的是后向工作: 从表明{P}C{Q}的目标开始, 我们生成子目标, 子目标, 如此反复直至问题解决. 例如, 假定我们想要证明: ⊢ { X=x ∧ Y=y } R≔X ; X≔Y ; Y≔R { Y=x ∧ X=y } 那么根据赋值公理和顺序规则, 证明以下子目标就足够了: ⊢ { X=x ∧ Y=y } R≔X ; X≔Y { R=x ∧ X=y } 鉴于⊢{R=x∧X=y}Y≔R{Y=x∧X=y}. 根据类似的论证, 这个子目标可以被归约为 ⊢ { X=x ∧ Y=y } R≔X { R=x ∧ Y=y } 这显然可由赋值公理推出.

这一章描述了如何形式化这样一种面向目标的证明方法.

这里所描述的验证系统可以被视为一个证明检查器, 同时它也为证明的生成提供了一定的帮助. 下图给出了该系统的概览.

要证明的规约 →人类专家 注解了的规约 →vc生成器 逻辑陈述集合 →定理证明器 简化的验证条件集合 →人类专家 证明结束

该系统的输入是一个部分正确性规约, 其中标注了描述变量之间关系的数学陈述. 系统从标注后的规约中生成一组纯数学陈述, 称为验证条件 (即VC). 在3.5节中将会证明, 如果这些验证条件是可证明的, 那么原始规约就可以从Hoare逻辑的公理和规则中推导出来.

验证条件被传递给一个定理证明器程序, 该程序尝试自动地证明它们; 如果证明失败, 则向用户寻求建议. 我们将集中讨论与Hoare逻辑相关的方面, 而对定理证明本身着墨甚少.

当前大量研究的目标是构建能够将缓慢且昂贵的人类专家的参与降到最低的系统. 这可以通过以下途径实现:

  • 减少所需标注的数量和复杂度, 以及
  • 增强定理证明器的能力.

下一节将解释验证条件的工作原理. 在3.5节中, 将依据Hoare逻辑的公理和规则来论证其使用的合理性. 除了作为机械化验证系统的基础之外, 验证条件也是手工进行证明的一种有用方式.

第3.2节 验证条件

以下各节描述了如何将面向目标的证明风格形式化. 为了证明一个目标{P}C{Q}, 需要完成三件事. 这些将在后文中详细解释, 但这里先给出一个简要概述:

  1. 通过在程序C中插入陈述 (通常称为断言) 来对其进行标注, 这些断言表达了在各个中间点上应当成立的条件. 这一步骤是棘手的, 需要智慧以及对程序工作方式的深刻理解. 将其自动化是一个人工智能问题.
  2. 然后从标注后的规约中生成一组称为验证条件 (简称VC) 的逻辑陈述. 这一过程是纯机械的, 很容易由程序完成.
  3. 证明这些验证条件. 将其自动化同样是一个人工智能问题.

我们将证明, 如果能够证明由{P}C{Q}生成的所有验证条件 (其中C已被适当注解), 则⊢{P}C{Q}.

由于验证条件只是数学陈述, 可以将上述第2步视为将验证问题编译或翻译为传统数学问题的过程.

第3.5节 验证条件的澄清

本节将证明, 若一个带注解的规约{P}C{Q}所生成的验证条件是可证的, 则该规约在Hoare逻辑中也是可证的, 即⊢{P}C{Q}. 这说明验证条件是充分的, 但并不意味着它们是必要的. 事实上, 验证条件是最弱的充分条件, 但我们在此既不对此作更精确的表述, 也不深入讨论细节. 关于前条件的深入研究可参见Dijkstra的著作 [8].

容易证明验证条件不是必要的, 即{P}C{Q}的验证条件不可证并不意味着⊢{P}C{Q}不可推导. 例如, 带注解规约{T}WHILEFDO{F}X≔0{T}的验证条件是不可证的, 但该Hoare三元组在Hoare逻辑中是可证的.

验证条件充分性的论证将对C的结构进行归纳. 这类归纳论证包含两个部分. 首先, 证明结论对赋值命令成立. 其次, 证明当C不是赋值命令时, 若结论对C的各组成命令成立 (这称为归纳假设), 则结论对C也成立. 前者称为归纳基础, 后者称为归纳步骤. 由归纳基础和归纳步骤即可得出结论对所有命令成立.

第3.5.1小节 赋值

{P}V≔E{Q}唯一的验证条件是P⇒Q[E/V]. 如果这是可证的, 那么鉴于⊢{Q[E/V]}V≔E{Q} (赋值公理), 根据前条件强化可以推出⊢{P}V≔E{Q}.

第3.5.2小节 条件式

如果{P}IFSTHENC1ELSEC2{Q}的验证条件是可证的, 那么{P∧S}C1{Q}和{P∧¬S}C2{Q}的验证条件都是可证的. 根据归纳假设, 我们可以假定⊢{P∧S}C1{Q}和⊢{P∧¬S}C2{Q}. 因此, 根据条件式规则可得⊢{P}IFSTHENC1ELSEC2{Q}.

第4章 可靠性和完备性

本章研究了Hoare逻辑的公理和规则是否正确 (可靠性) 以及是否充分 (完备性) 的问题. 这要求明确地给出编程语言的意义 (语义), 从而能够严格地定义Hoare三元组的语义.

第4.1节 语义

一条命令C将一个初始状态转换为一个最终状态 (或者不终止). 对于目前所描述的语言, 从一个给定的初始状态出发, 至多只能到达一个终止状态——即命令是确定性的——但后面当我们向语言中加入存储分配时, 情况就不再如此了. 在数学上, 有几种本质上等价的方式来表示命令的意义. 我们将使用关系, 但部分函数也是常用的方式. 使用关系通常与操作语义相关联, 而部分函数则与指称语义相关联, 不过这并不是严格固定的: 指称语义可以使用关系作为指称, 操作语义也可以归纳地定义函数. 事实上, 在下面的第4.1.2节中, 我们给出了一种命令的指称语义, 其中指称就是关系.

各种风格的语义在很大程度上只是表示相同数学思想的不同方式. 某些数学表示更适合某些目的, 而另一些表示则更适合其他目的. 我在下面给出的语义可能与你在之前课程中见过的语义一致, 也可能不一致. 如果它看起来不同, 那么一个很好的练习就是思考它们之间有何关联.

第4.1.1小节 表达式和陈述的语义

命令中可能包含表达式或陈述: 表达式出现在赋值的右侧, 而陈述出现在条件语句和WHILE命令的测试条件中. Hoare三元组的前条件和后条件也是陈述. Hoare逻辑的经典处理建立在一阶逻辑之上, 表达式被视为逻辑中的项, 陈述被视为公式. 你应该在之前的课程中已经熟悉了一阶逻辑的语义, 我不想在这里重复那些内容. 此外, 在现代应用中, 用于书写前条件和后条件的语言有时比一阶逻辑更弱或更强, 例如无量词逻辑 (更弱) 或高阶逻辑 (更强).
